# 0002 — 成品菜肴的第④级兜底策略

**状态**：已接受（已同步 SPEC §1/§2.1/§4.4.2/§7.2/§7.4/§7.6/§7.9/§8/§8.2/§8.5）
**日期**：2026-08-17
**关联**：SPEC §7.2（四级查询链）、§4.4（外部食物库）、PRD §1.4、[0001](0001-llm-provider.md)（模型路由）

## 背景

SPEC §7.2 当前定义第④级为「网络搜索证据 + LLM 结构化估算，标记 `web_estimate`」。本决策核查：第②③级（中国 OCR 库、USDA）对成品中式菜肴（如干煸四季豆、麻婆豆腐）命中率如何？如果两者结构上就覆盖不到，第④级该是「网络搜索兜底」还是「LLM 拆解菜肴为原型食物组成 + 克重，逐项复用前三级」？

## 调研发现

### 1. 中国 OCR 库（`food_base_cn`）结构性只覆盖原型食物

[Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data) 的 `json_data_vision_251206_Qwen2-5-VL-72B-Instruct` 目录，61 个文件全是原料大类（畜肉/禽肉/蛋/奶/蔬菜/水果/坚果/干豆/菌藻/薯类/谷物/油脂/鱼虾蟹贝等），没有「菜肴类」。抽样 `merged_干豆类及其制品-绿豆.json`：条目是「绿豆（干）」「绿豆面」「绿豆饼」这类原料/初级加工品，不是「麻婆豆腐」这种成品菜。

根源：这份数据是把《中国食物成分表标准版（第六版）》「能量和食物一般营养成分」章节截图 OCR 成 json，该表编制目的就是原型食物营养参考，不是菜谱数据库（README 确认）。1677 条数据，SPEC §4.4.1 已有接入注意点（`Tr`/破折号不能转 0、`edible%` 用法等）不受影响。

顺带核实：这个版本已是仓库能给的最优版本——查提交历史，是最新一次提交，是同一模型对更早版本 `json_data_vision`（含字段错位的婴幼儿食品分类）的清理修复；README 记录作者 A/B 测过 Qwen2.5-VL-72B-Instruct vs Qwen3-VL vs GLM-4.5V 这个 OCR 任务，前者胜出。SPEC §4.4.1 选型不用变。

### 2. USDA 实测：成品菜命中率低，强依赖英文查询词

用 `FoodData_Central_API_KEY` 实测 `/foods/search`：

| 查询（中文原意） | 结果 |
|---|---|
| kung pao chicken（宫保鸡丁） | 命中 `Survey (FNDDS)` "Kung pao chicken"、`SR Legacy` "Restaurant, Chinese, kung pao chicken" —— 有效 |
| sweet and sour pork ribs（糖醋排骨） | 命中 `Survey (FNDDS)` "Sweet and sour pork"、`Foundation`/`SR Legacy` "Restaurant, Chinese, sweet and sour pork" —— 有效 |
| mapo tofu（麻婆豆腐） | 「Tofu yogurt」「Mayonnaise made with tofu」，无关 —— 未命中 |
| beef with scallion（葱烧牛肉） | 只命中葱、牛肉原料条目，无成品菜 —— 未命中 |
| dry-fried green beans（干煸四季豆） | 「Fried green beans」「Fried green tomatoes」，做法对不上 —— 未命中 |
| salt and pepper tofu（椒盐豆腐） | 「fuyu 腐乳」「豆腐酸奶」等无关制品 —— 未命中 |
| scallion oil noodles（葱油拌面） | 葱/面条原料及不相关 branded 商品 —— 未命中 |
| big plate chicken xinjiang（新疆大盘鸡） | 关键词 "big" 命中 McDonald's Big Mac 系列，纯噪声 —— 未命中 |
| sauerkraut fish soup（酸菜鱼汤） | 泛泛的「Soup, fish or shrimp」，对不上具体菜 —— 未命中 |

9 个中式家常/地方菜（同 0001 拍照测试那批：干煸四季豆、新疆大盘鸡、椒盐豆腐、葱烧牛肉、酸菜鱼……）里只有 2 个美式中餐馆经典款命中有效成品菜条目，其余只有原料级或噪声结果——「第②③级大概率覆盖不到成品菜」是可复现结论，不是猜测。

顺带确认三个此前 SPEC 未展开的实操点：

- USDA 搜索必须用英文——中文原文基本查不到相关结果，查询链路需要「中→英」翻译步骤（当前 SPEC §7/§8 未定义在哪一步做，需要补）。
- `foodNutrients` 数组混有占位行（如 `id=2045 name="Proximates" amount=undefined`），验证了 SPEC §4.4.2 的警告确有必要：必须按 nutrient id+名称+单位精确匹配，不能假设数组位置。
- `X-RateLimit-Remaining` 从 3599 起随每次请求递减 1；文档写「每小时 1000 次」，实测起始值更高，具体配额以响应头为准。

### 3. 参考实现 calzen-ai-app：直接抛弃数据库，纯 LLM 知识估算

[leetrip4171-gif/calzen-ai-app](https://github.com/leetrip4171-gif/calzen-ai-app) 的 `server/food-analysis/food-analysis.analyzer.claude.ts`：单次把照片喂给 Claude，prompt 直接要求模型对每样食物吐出 `calories`/`carbsG`/`proteinG`/`fatG` 绝对值，最多 5 个代表食物，无参照物克重估算，无成分拆解，无外部数据库或网络搜索。

其决策记录 `decisions/2026-08-06-spec-vision-model.md` 给的理由是「结构简单、避免识别 API+营养库两段式误差叠加、MVP 目标是大致 calorie 合计」，并写明「实测精度不够就换专用营养分析 API」——作者自己也当作简单度权衡，不是验证过的最优解，且目标精度比 DietApp（要精确到每餐 g 级四级查询+人工确认）粗得多。

这证明「直接信任 LLM 自身营养知识」是已经在生产里跑的路径，但不能照抄——它跳过的参照物估重、按原料拆解、可信度分级恰是 PRD/SPEC 定好、不该退让的部分。它更适合作为「拆解兜底」可行性的佐证：连「整道菜直接问 LLM 要营养值」都能在生产环境用，那「LLM 只拆解原料清单+克重、营养值仍查权威库」的确定性只会更高。

### 4. 模型档位实测：文本统一用 qwen-plus，不开思考模式

用同一个 key 测了 8 个候选文本 alias（`qwen-flash`/`qwen-plus`/`qwen-max`/`qwen3.5-plus`/`qwen3.6-flash`/`qwen3.7-plus`/`qwen3.7-max`/`qwen3-max`），全部 200 可用，响应 `model` 字段各自独立回显，确认是互相独立的模型条目。`qwen-plus`（国内版约 ¥0.8/百万输入 token，输出 3–5 倍，贵于 flash 但远低于 max）和 `qwen-flash` 一样是不带版本号的滚动别名，延续 0001「优先不带版本号别名、避免手动追踪弃用」的原则。

**思考模式实测：对拆解类任务是负优化。** 本假设"拆解需要推理，该开思考模式"，实测推翻：同一拆解提示词（"红烧排骨"拆原料+克重）对比开关思考模式：

| 配置 | 输出质量 | 总 token |
|---|---|---|
| flash 不思考 | 9 项，带做法说明 | 236 |
| flash 思考 | 8 项，说明消失，电报体 | 1675（1508 是思考消耗） |
| plus 不思考 | 12 项，含单位换算依据、备注排除项，最完整 | 543 |
| plus 思考 | 10 项，说明同样消失 | 2516（2284 是思考消耗） |

两个模型开思考后答案反而更简短、解释更少，token 成本却暴涨 7–10 倍——拆解菜谱是知识复述+列举，不是多步演绎推理，思考模式没有加成。`qwen-plus` 不思考本身就比 `qwen-flash` 输出更完整。

**延迟实测**（§8.1 这类简单解析任务，各 3 次取均值）：flash 786ms，plus 936ms，慢约 20%。0001 已定价格在此用量级不构成决策依据；延迟差距可接受，且能少维护一档模型配置——**最终选择：纯文本统一用 `qwen-plus`（不开思考模式），不再区分"简单文本用 flash、拆解用 plus"，只保留"文本 vs 图片"两条路由，含图片仍用 `qwen3-vl-plus`。** 0001 需要同步更新路由表。（另观察到一次 flash 把"清蒸鲈鱼"简化成"鲈鱼"丢了做法信息、plus 保留了；单样本不下结论，留作后续观察。）

## 决策（讨论稿，待确认）

**倾向方案分两层，外层工作流、内层工具调用：**

- **外层四级链保持确定性 workflow，顺序不变**：个人常吃库 > 中国库 > USDA > 第④级，任一级有候选就停，不因响应快慢抢跑，不让 LLM 自主决定要不要跳级——对应 AGENTS.md「四级链顺序不可改」铁律，本决策不碰这条。
- **第④级内部改造**：从「网络搜索证据 + LLM 估算」改成「LLM 拿到 `query_food_base_cn`/`query_usda`/`web_search` 三个工具，把菜拆解为原型食物组成（含调料）+ 克重，同一轮按需并发调用工具逐项查询，查不到的单项才退回 LLM 估算」。网络搜索从"整道菜的营养数值来源"降级为"单项查不到时的兜底工具"，或用于校准拆解本身（如某道菜标准做法通常放多少主料/糖），**不用于直接给出或佐证最终热量数字**。营养加总仍由后端代码完成，LLM 不直接产出最终营养值（单项估算例外，按现有 `web_estimate` 方式标记置信度）。
- **拍照入口不能只把菜名传给第④级，要把 §8.2 识别时看到的东西一并带过去**：§8.2 照片识别这一步（`qwen3-vl-plus`）现在的输出不能只有菜名，还要给一段开放式的视觉描述——看到的原料/配菜、酱汁颜色和覆盖程度、油光/油量观感、口味偏重/清淡的直观印象等，**不锁死成固定字段枚举**，让 VL 自由描述实际看到的内容，不同的菜该说的东西本来就不一样。这段描述作为自由文本，和结构化字段（食物名/克重/置信度等）并列，不强行拆成预定义字段。进入第④级时，把这段视觉描述和菜名一起作为上下文传给 `qwen-plus`，让拆解基于"这次实际看到的这道菜"，而不是只拿一个菜名去套泛化菜谱知识。文本入口（没有照片）的成品菜没有这段描述，仍只能靠菜名+菜谱知识拆解。
- **模型路由**：按单次调用是否带图判断，不看用户走的是文本还是拍照入口——第④级拆解这一步本身只处理已识别出的菜名文字、不再传图，即使这条记录源头是照片也算"不含图片"，走 `qwen-plus`（不开思考模式）；只有真正携带图片的那次调用（§8.2 照片识别本身）才用 `qwen3-vl-plus`。理由和实测见"调研发现 4"，0001 路由表已同步这条判断标准。
- **拆解说明走聊天文字回复，不进 Confirm 结构化字段**：例如"识别出'红烧排骨'，大概 xxg 排骨（带骨），约 xx kcal；调味主要食用油/酱油/冰糖，偏重口，约 xx kcal；合计约 xx kcal"作为一条对话消息展示。Confirm 弹窗保持 §7.4/§8.2 已有的精简字段（食物名/克重/热量/置信度），不塞入逐项拆解明细。

理由：

1. 第②③级已证实的强项是原型食物覆盖（中国库 1677 条原料、USDA Foundation/SR Legacy 原料条目丰富），拆解后每个组成项本该落在这两级，直接复用已建好的四级链和 §4.4 取值规则，不新造链路。
2. LLM 的职责从「直接背出这道菜多少大卡」收窄成「列出常见做法的原料+大致克重比例」——更贴近 LLM 对中餐做法的知识分布（复述菜谱套路 vs 记忆精确营养数字），可信度更高，也更容易被用户在 Confirm 界面逐项修正，而非只能整体接受/拒绝一个黑箱总数。
3. 网络搜索作为"这道菜的营养数据源"本身不可靠——不同菜谱博主的调料比例、用油量差异很大；calzen-ai-app 的实践证明"直接问 LLM"在生产里也扛得住，拆解方案的确定性只会更高不会更低。
4. 拆解结果对应 §4.5 `food_favorite.components` 已有的「食物名+克重+raw/cooked」结构，后续存成个人食谱不需要另建数据形状。
5. 不用全自主 agent 重排四级顺序：直接违反已定顺序铁律；"自由发挥"和"工作流里挖几个 LLM 决策点"本质一样，前者只是多绕一圈，还丢失可测试性。
6. "多轮来回试"本身不产生新信息——除非某次重试真的调用新工具拿到新数据，否则重试三次和一次期望质量相同，只是徒增延迟和费用。真正需要的是"该不该多查一个工具"这种有信息增量的判断，交给 LLM 的工具调用决策，不需要开放式循环。
7. 拆解容易低估隐性用油/糖盐，这条经验规则直接写进 prompt（按估算克重乘上调系数），比指望 agent 在循环里"悟出"这个偏差更可靠也更省钱。
8. 中国库和 USDA 的 HTTP 查询可以并发发出以降低延迟，只要候选筛选逻辑仍严格遵守"中国库优先于 USDA"，这是纯实现层优化，不需要写进 SPEC。
9. **不采纳"LLM 自己综合网络搜索结果和照片视觉估算、取平均得出最终热量"**：这等于让 LLM 重新变成营养数值的最终来源，违反"LLM 不得生成营养值"和理由 3。两个来源并不独立——网络菜谱和 LLM 训练语料高度重叠，平均两个可能共享同一套偏差的估计，不等于统计学上平均独立样本降方差，更可能是"两个不准的数字加权出一个听起来更可信、但一样不准、还没法校验"的数字。网络搜索该做的是帮拆解找依据（校准某道菜标准做法的主料/糖比例），克重定下来后热量仍走第②③级查表由后端算，不是 LLM 直接报数字。

**已收敛**（原来是开放问题，随上面方案一起定了）：单个原料查不到 → 退回该原料自己的估算+置信度标记，不是整道菜判 `web_estimate`；隐性调料/用油必须给出估算并上调，不允许省略；网络搜索保留但只做第④级内部工具（查原料/校准比例），不作为营养数值或最终热量的直接/佐证来源；拆解过程走聊天文字回复，Confirm 界面不展示逐项拆解明细；纯文本（含拆解）统一 `qwen-plus` 不开思考，不再区分 flash/plus 两档；§8.2 照片识别输出补一段开放式视觉描述（不锁死字段），第④级拆解时和菜名一起作为上下文。
