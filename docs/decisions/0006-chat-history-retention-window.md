# 0006 — 对话历史保留窗口：1 天还是 7 天

**状态**：已接受（2026-08-23 已同步 SPEC §6.1/§6.4/§11.1、PRD §5.1/§9.1）
**日期**：2026-08-22
**关联**：SPEC §6.1（结转与清理边界）、§6.2（补录/修改）、§6.4（对话历史）、§8.3（补录对话契约）、`tasks/current.md`（1.9 写入+今日明细 UI，`today_context` 设计依赖本决定）

## 背景

现状 SPEC §6.1/§6.4 把 `chat_message` 的清理边界和 `meal_entry`/`exercise_entry` 绑在一起：结转成功后统一"删除 `date < B−6` 的餐次与聊天"，两者都保留"当前归属日 + 前 6 天"共 7 天。

1.9（写入 + 今日明细 UI）设计"普通录入"环境下喂给 LLM 的 `today_context` 时，你提出"只保留一天的历史聊天记录"——这实际上是在改 SPEC 已经写死的 7 天口径，值得单独拉出来想清楚，而不是顺手在实现计划里改掉这个假设。

## 要回答的两个问题

1. `chat_message` 到底要不要保留 7 天？（存储保留窗口本身）
2. 缩短它会不会连带削弱 §6.2/§8.3 定义的"最近 7 天补录/修改"能力？（功能依赖检查——这条不查清楚，缩短保留期可能是拆共享地基的坑）

## 调研发现

### 1. `chat_message` 的 7 天目前只是"跟着 `meal_entry` 一起清理"，没有独立存在的理由

§6.1 原文是"成功结转后删除 `date < B−6` 的餐次**与聊天**"——两张表焊在同一次清理动作里，读起来像是实现上顺手一起删，不是"聊天记录本身需要保留 7 天"这个产品判断的直接推论。翻遍 SPEC/PRD，找不到一处业务需求明确要求"用户需要翻看 3 天前的聊天气泡"。

### 2. §8.3 补录对话契约的 LLM 上下文来自 `meal_entry`，不是 `chat_message`

这是最关键的一条。§8.3 写明"后端提供**目标日现有明细**作为上下文，LLM 输出增删改操作"——"现有数据"指该日已写入的 `meal_entry` 行，不是那天的原始聊天记录。§6.2 补录预览展示的也是"现有明细 + 待确认变更"，同样是 `meal_entry` 视角。

也就是说：**补录/修改功能真正依赖的 7 天窗口是 `meal_entry` 的，`chat_message` 保不保留 7 天，和这个功能能不能跑通无关**。这条结论直接推翻了"两者必须绑在一起清理"的隐含假设——完全可以让 `meal_entry`/`exercise_entry` 继续保留 7 天（A1/A2 图表默认窗口也需要），单独把 `chat_message` 的保留期改短。

### 3. 缩短保留期，和"这是记账工具、不是聊天工具"的定位一致

产品的权威记录一直是结构化的 `meal_entry`/`daily_summary`；聊天气泡只是"怎么录进去的"这个过程的留痕，不是终态数据。今日明细表、A1/A2 图表、补录预览，读的全是结构化表，没有一处 UI 需要回放"3 天前聊了什么"。缩到 1 天（= 当前归属日），聊天记录的作用收敛成"今天这一轮录入过程的可见状态"，和 §6.4 已经定的"显示历史不等于模型上下文"是同一个方向上更进一步的收紧。

### 4. 缩短后，1.9 的 `today_context` 设计反而更简单

1.9"普通录入"环境要把当天完整对话历史喂给 LLM 做上下文。如果 `chat_message` 本来就只保留 1 天，"当天完整对话历史"和"`chat_message` 表里能查到的全部历史"就是同一件事，不需要额外写"只取最近 N 条/按 token 数截断"这类逻辑——存储策略和上下文策略直接重合，少一层容易出 bug 的过滤代码。

### 5. 代价：清理任务从"一个边界"变成"两个独立边界"

现状结转任务一次 DELETE 处理两张表、共用 `B−6` 这一个边界；改动后需要两个边界：`meal_entry`/`exercise_entry` 仍是 `date < B−6`，`chat_message` 改成 `date < B`（只留当前归属日）。这不是架构复杂化，只是把偏移量从 1 个常量变成 2 个——1.9 的 plan 里已经把归属日偏移量做成 `Settings` 里的配置项，照同样方式加一个 `chat_retention_days`（默认 1）即可，不需要新机制，1.10 实现结转任务时两个边界分别读各自配置、分别 DELETE。

### 6. 需要明确承认的取舍

- 缩短后，用户如果想回看"上周三具体是怎么跟 AI 描述那顿饭的"，聊天气泡已经不在了，只能看到 `meal_entry` 里的结构化结果（食物名/克重/热量快照），看不到当时的原话。这是唯一被牺牲的能力，目前 SPEC/PRD 都没有把它列为需求，但明确写下来免得以后忘了这是有意为之。
- 如果以后想加"导出/回放完整聊天记录"这类功能（PRD 目前未提及），1 天保留会直接堵死这条路，需要在真的有这个需求时重新评估，而不是现在想当然认为随时能改回去（改回去要动的是清理任务的行为，不是简单调个数字——已经删掉的历史找不回来）。

## 决策

`chat_message` 保留窗口从"随 `meal_entry` 一起保留 7 个归属日"改为**只保留当前归属日（1 天）**：

- 清理边界拆成两条：`chat_message` 用 `date < B` 清理（`B` = 当前归属日），`meal_entry`/`exercise_entry` 保持 `date < B−6` 不变；两个边界共用同一个 `attribution_date()` 计算逻辑，只是保留天数配置不同（`chat_retention_days=1` vs 明细/运动的 7 天）。
- `meal_entry`/`exercise_entry`/`daily_summary` 的保留策略不变——这条决策只动聊天记录，不动任何结构化业务数据。
- §6.2/§8.3 的"最近 7 天补录/修改"不受影响：其 LLM 上下文来自 `meal_entry`，不来自 `chat_message`（见"调研发现 2"）。
- 1.9 的 `today_context` 设计据此简化：不需要额外截断逻辑，"当天"和"`chat_message` 里存在的全部历史"天然重合。

## 后果

- **SPEC 需要同步**（本决策一旦确认接受）：§6.1（清理边界拆成两条）、§6.4（"按归属日保留 7 天"改成"只保留当前归属日"）；§2.1/§11.1/§12.1 等提到"对话…7 天"的措辞需要逐处检查，确保"聊天保留期"和"补录/修改的 7 天窗口"不再共用同一个数字、不再被读成同一件事。这是共享地基改动（碰 SPEC §6），按 AGENTS.md 应该单独开分支先合，不在 `feature_demo_04_write_path` 里顺带改 SPEC 正文。
- `Settings` 新增 `chat_retention_days`（默认 1）；`meal_entry`/`exercise_entry` 的 7 天口径不变，两者在 1.10 结转任务里分别落地。
- 1.10 结转/清理任务实现时需要按两个边界分别 DELETE，不能再复用同一条 SQL/同一个偏移量。
- Demo 阶段（1.9）不直接受影响——Demo 本来就不支持补录（§11.1 已限定"只允许当天新增"）。这条决策现在定下来，是为了让 1.9 的 `today_context` 设计有据可依，不用等 1.10 结转任务落地时再回头改一遍已经写好的代码。
