# 0001 — 多模态 LLM API 供应商选型

**状态**：已接受
**日期**：2026-08-16（验证完成 2026-08-17）
**关联**：PRD §5.2/§5.3、SPEC §7/§8.8

## 背景

SPEC §8.8 已定方向：模型需支持中文、多图输入、可靠结构化输出，Qwen3-VL 系列为首选候选，具体供应商/版本留给独立 ADR。硬约束：

- 中式家常菜识别与克重估算主要靠 LLM，非数据库兜底（PRD §1.4）
- 严格 JSON 输出，解析失败回退追问（SPEC §8）
- LLM 只做识别/归一/消歧，不生成营养值（SPEC §7）
- API Key 只留私有后端；供应商需支持关闭训练或满足数据保留要求（SPEC §6）
- 后端做供应商无关适配层，选型不是焊死的（SPEC §5.3/§8.8）
- 限定中文/国产 LLM API，海外供应商不在候选范围（用户要求）

## 调研发现

- **国产多模态候选**：阿里云百炼（Qwen-VL/Qwen3-VL）、智谱 GLM-4.6V(-Flash)、字节火山引擎豆包视觉。三家都是 OpenAI 兼容接口、支持多图输入、支持某种 JSON 结构化输出。DeepSeek 排除——无生产级托管多模态 API（DeepSeek-VL2 只是开源权重）。
- **结构化输出边界**：文档查到的信息（"JSON Schema 强约束只开放给纯文本 Plus/Max 档，`qwen-flash` 只有 JSON Object 模式"）与实测不符——2026-08-17 真实调用证明 `qwen-flash` 的 Object 和 Schema 两种模式都能用。网上信息不完全可信，这次靠实测纠正了。不管哪种模式，字段结构仍要靠后端 Pydantic 校验 + 失败追问兜底，不能无条件信任模型输出。
- **价格对比**（个人用量级，差异可忽略，仅供参考）：
  - 阿里百炼 `qwen-flash`（纯文本）：¥0.15/¥1.5 每百万 tokens（输入/输出，≤128k 档位）
  - 阿里百炼 `qwen3-vl-plus`（视觉）：¥1–3/¥10–30 每百万 tokens，按上下文阶梯计费
  - 智谱 GLM-4.6V：¥1/¥3 每百万 tokens（较上一代降价 50%）
  - 火山引擎豆包视觉：¥0.6–1.8/¥3.6–10.8 每百万 tokens（按子型号浮动）
  - 换算下来个人使用场景每月大概率是个位数到十几元人民币，价格不构成决策依据。
- **数据保留政策**：阿里云百炼**按量付费 API** 和 **Token Plan 团队版**承诺不将调用数据用于训练，传输走 AES-256 加密；**Token Plan 个人版没有这个承诺**（数据会用于"服务改进与模型优化"）——这一条直接排除了个人版套餐。
- **拍照估重能力的证据**：曾以为"中国食物成分数据是用 Qwen2.5-VL 做 OCR 生成的"能说明 Qwen 系列擅长处理中餐图片，但 OCR（文字/表格抽取）和"认出菜品 + 用参照物估算体积"（物体识别 + 空间推理）是不同能力，这条论据不够硬，改用更贴题的证据：Qwen3-VL 在第三方空间推理榜单 **SpatialBench** 排名第一（13.5 分，高于 Gemini 3.0 Pro Preview 的 9.6 和 GPT-5.1 的 7.5），在 **VSI-Bench**"物体尺寸估计"子项也表现较强——这两个都直接对应"参照物估克重"的机制本身。但当时没有中餐菜品识别的专项 benchmark，这个空白后来靠 2026-08-17 的小样本实测补上（见下方"验证记录"）。

## 决策

**主选：阿里云百炼（DashScope）**，按**这一次 API 调用本身的输入内容**（不是用户这次录入走的是文本入口还是拍照入口）路由到两个滚动 alias（不用带日期的 pinned 快照，规避下线风险）：

- 这次调用不含图片 → `qwen-plus`（不开思考模式）。覆盖 §8.1/§8.3/§8.4/§8.6/§8.7，以及 §7.2 第④级拆解推理——**包括入口是拍照、但这一步只是拿已识别出的文字信息做拆解/推理、本身不再传图的情况**（例如：照片先过 `qwen3-vl-plus` 识别出"红烧排骨"及其视觉描述——酱汁颜色偏深、油光明显、配菜里看到土豆块——随后第④级把菜名+这段描述一起交给 `qwen-plus` 做原料拆解，这一步不带图片，走 `qwen-plus`，不是 `qwen3-vl-plus`；这段视觉描述本身的产出规则见 [0002](0002-composed-dish-fallback.md)）。
- 这次调用含图片 → `qwen3-vl-plus`（§8.2 照片估算；独立视觉专精系列，非通用文本线，拍照估重是精度要求最高的一环，值得用专精模型）

判断标准是单次调用的输入是否带图，不是整条用户流程的入口——同一次拍照记录里，"识别照片"和"基于识别结果做后续文本推理"是两次不同的调用，各自独立路由。

原计划纯文本用更便宜的 `qwen-flash`，实测也验证可用（见下方验证记录），但 0002 为第④级拆解选型时发现：思考模式对拆解类任务是负优化（两个模型开思考后输出反而更简略、token 成本涨 7–10 倍），且 `qwen-plus` 不思考本身就比 `qwen-flash` 输出更完整；延迟只慢约 20%（786ms→936ms），在个人用量级不值得为省这点延迟多维护一档模型配置，遂将纯文本统一收敛到 `qwen-plus`。实测细节见 [0002 调研发现 4](0002-composed-dish-fallback.md#4-模型档位实测文本统一用-qwen-plus不开思考模式)。

不跨供应商拆分（不用 DeepSeek 处理文本 + 另一家处理图片）——维护两套供应商的成本对个人项目不值得，价格差异在这个调用量级也可忽略。

选择理由：
1. Qwen3-VL 在 SpatialBench/VSI-Bench 空间推理与尺寸估计上领先，贴合"参照物估克重"的机制
2. OpenAI 兼容接口成熟，适配层落地成本低
3. 按量付费模式明确承诺不用于训练，满足 SPEC §6；**必须用国内站 Key，国际站不兼容**
4. 原生多图输入，覆盖多视角合并识别需求
5. 同系列 `qwen-flash` 已实测支持 JSON Object 与 JSON Schema 两种结构化输出模式（¥0.15/¥1.5 每百万 tokens），确认百炼的结构化输出机制在这个价位档就已可用；纯文本实际选型见上方 `qwen-plus` 收敛说明

**备选**：智谱 GLM-4.6V（Function Calling 原生融入视觉模型，价格同样低），供应商无关适配层可在后续接入作为故障转移/成本对比。

**排除**：DeepSeek（无生产级托管多模态 API）、海外供应商（不满足中文优先前提）、百炼 Token Plan 个人版（不满足不训练承诺）。

## 验证记录

**2026-08-17 真实 API 调用**：`qwen-flash`（JSON Object + JSON Schema 均通过，结构化输出机制验证有效）与 `qwen3-vl-plus`（图片输入 + JSON 通过）均验证可用，价格与预期一致。踩坑记录：JSON Object 模式要求 prompt 含小写 "json"；图片建议传 base64，外部 URL 会在阿里云服务器侧下载超时；账号必须是国内站按量付费 Key。（`qwen-flash` 本身验证结果仍然成立，只是纯文本路由后来按 0002 的实测收敛到了 `qwen-plus`，见上方"决策"。）

**2026-08-17 中餐识别小样本测试**（9 张真实照片，含 1 张多菜合影、1 张手掌参照物）：结构性能力扎实——JSON 100% 合法、置信度校准正确（无参照物降级、有参照物升到 high）、多菜合影正确拆分为独立条目。菜名识别有实打实的错误率（约 1/3，如漏认食材、认错具体菜名），但 SPEC §7.7/§8.2 本来就要求用户在 Confirm 前检查修改食物名称和克重，这个错误率对"LLM 提案 + 人工确认"的流程是可接受的起点。**结论：接受本决策**，不阻塞实现。

## 后果

- 后端实现供应商无关适配层，第一版对接百炼 OpenAI 兼容 endpoint，按"是否含图片"路由模型；两条路径都必须过 Pydantic 校验 + 失败追问兜底，不能假设结构化输出模式能替代校验。
- 账号开通用按量付费 Key（国内站），不能用个人版 Token Plan 或国际站 Key。
- 具体模型子版本、价格随官方迭代变化快，本 ADR 不追踪最新数字，后端配置里的 alias 才是唯一真源。
- 若后续实际使用中菜名识别错误率影响体验，GLM-4.6V 可直接提到主选位置，适配层已为此留好余地。
