# 减脂软件 · 产品需求文档 (PRD)

**版本**：v2.15（产品形态统一为手机 UI PWA + 单用户私有后端；重构后期里程碑）
**用途**：产品需求定义，作为后续技术 Spec（`DietApp_SPEC.md`）的输入
**产品形态**：手机 UI 的可安装 PWA（个人自用）——业务数据由单用户私有后端持久化；不做宽屏专属适配，不开发原生 App（节奏见 §9）

---

## 1. 产品概述

### 1.1 市场背景

- **市场规模**：基于超过 1786 万人体检数据，中国成年人超重/肥胖检出率达 51.4%（男性 63.3%，女性 39.1%），单纯肥胖率 16.3%——潜在用户是「半数成年人」级别的盘子。
- **政策东风**：国家卫健委 2024 年发布《肥胖症诊疗指南（2024 年版）》《体重管理指导原则（2024 年版）》，并将 2024–2027 定为「体重管理年」，官方首次系统性推动全民体重管理。
- **付费能力**：功能性瘦身食品市场 2022 年约 3387 亿元（同比 +21.2%），预计 2024 年达 4744.5 亿元；消费者瘦身意愿支出最集中在 2001–4000 元区间（32.7%）——用户不仅有需求，也愿意为体重管理付费。（艾媒咨询《2023-2024年中国健康瘦身行业市场运行及投资布局监测分析报告》）

三者合起来：市场足够大 + 政策推动 + 付费意愿强，是值得投入的方向。

### 1.2 用户画像

- **数据支撑**：健康/运动类 App 用户女性占比超六成、消费水平偏高（个推大数据）；减脂人群中女性是绝对主力、男性参与度偏低（瘦吧《2023 年百万减脂人群洞察报告》：「女性主力军、男性躺平党」）；肥胖率随年龄上升，男性 40–49 岁达峰值，女性持续递增至老年，但主动用 App 记录的仍以中青年女性为核心。
- **典型画像**：
  - **主力用户「自律型减脂女生」**：22–35 岁女性，一二线城市，有明确减脂/塑形目标，愿意记录饮食、关注营养素，但苦于「记录太麻烦、算不清热量」——对应本产品的核心卖点：AI 对话式快速记录。
  - **次级用户「懒人型」**：想减肥但记录动力弱、易半途而废（男性与忙碌上班族居多）——对应本产品要解决的「降低记录门槛」痛点。
- **当前目标用户（实际范围）**：本产品定位为单用户个人自用；上述两类画像用于理解需求和判断功能价值，不代表当前路线图包含多人注册或公众发布。

### 1.3 使用场景

用户每天进行三餐 + 加餐的饮食记录、不定期的运动记录、体重体脂等身体数据记录，并定期（如每周）回看趋势做减脂复盘，而非每天盯着单日数字焦虑。

### 1.4 需求与痛点

- 传统热量记录 App 要手动搜索食物库、逐个填克数，操作繁琐、门槛高，是导致留存低、半途而废的主因（对应上文「懒人型」画像）；本产品用「对话式描述 + 拍照估算」替代逐项检索，降低记录门槛。
- 中式家常菜、复合菜品在通用食物数据库中覆盖差、误差大，需要专门的中式数据源与兜底机制，而不是仅靠 LLM 凭记忆估算（LLM 估算同一食物多次会漂移，长期追踪会累积误差）。
- 单日摄入波动大、容易造成焦虑或误判进度；不少用户还「看不懂数据、不知道怎么调整」，缺乏个性化反馈，只有历史堆叠而无解读，同样容易导致放弃。用户需要的是**趋势可见性**而非逐日打卡分数。

### 1.5 竞品分析

| 产品                 | 定位                | 体量                                  | 特点                                     | 短板（本产品的机会）                          |
| -------------------- | ------------------- | ------------------------------------- | ---------------------------------------- | --------------------------------------------- |
| 薄荷健康             | 饮食记录 + 代餐电商 | 累计用户约 1.2 亿（CBNData）          | 食物热量库全、记录功能成熟、靠卖代餐变现 | 记录仍偏手动；电商属性重，工具体验被稀释      |
| Keep                 | 综合运动健身        | 月活约 2653 万（QuestMobile，2024.6） | 课程内容 + 社区 + 硬件生态强             | 侧重「练」，饮食/热量记录不是核心，营养管理弱 |
| 咕咚 / 悦跑圈        | 跑步运动社交        | —                                    | 运动数据 + 社交                          | 几乎不覆盖饮食营养记录                        |
| MyFitnessPal（海外） | 饮食热量记录标杆    | —                                    | 食物库极大、记录标准                     | 手动录入繁琐、本土化食物差、中文体验弱        |

**差异化结论**：现有头部产品要么「重内容/电商」（薄荷、Keep），要么「重运动轻饮食」（咕咚、悦跑圈），饮食记录环节普遍停留在手动搜索 + 填克数的高门槛交互；本产品以 AI 对话/拍照录入为核心，直接切中这一共同短板。

**优先级逻辑**（对应 §3 功能与 §9 版本规划的取舍依据）：市场足够大 + 政策推动 → 值得投入；女性主力用户 + 记录门槛高是最大痛点 → 因此 §3.1 饮食记录以「AI 对话式录入」为主力（对应外部市场研究中的 P0），这是相对传统竞品「手动搜索 + 填克数」交互的核心差异点。市场研究中标注为 P1/P2 的方向（如个性化分析建议、提醒/打卡机制、食谱推荐、社区、硬件数据打通、付费方案）暂不在当前里程碑范围内（见 §9），可作为后续探索方向，但需专门评估后再纳入路线图。

> **需要留意的张力**：市场研究建议的 P1 方向包含「提醒/打卡机制」以对抗「懒人型」用户的流失倾向，但这与本产品当前的核心设计原则相冲突——§2 强调「不依赖社群监督或游戏化打卡」，§8 明确「不设计游戏化或社交监督机制，产品坚持度依赖用户自我驱动」。是否引入提醒机制、以及以何种非打卡式的方式设计（例如仅趋势提醒而非连续打卡计数），需要单独决策，本版本不默认采纳。

## 2. 产品目标

**一句话定位**：一款可从手机主屏幕直接使用、以自然语言/拍照对话录入为核心，并用长期热量与身体数据趋势驱动自我认知与坚持的个人减脂管理 PWA。

**预期效果**：

- 让用户能以最低摩擦、接近日常聊天的方式，持续积累准确、可信的饮食与身体数据。
- 让用户通过趋势曲线而非单日波动做判断，减少因单日超标/体重反弹造成的放弃。
- 引导长期可持续的热量缺口（避免过度激进节食），而不是短期极端瘦身。
- 让用户无需安装应用商店 App，即可从手机主屏幕进入完整产品；电脑浏览器仅作为同一手机 UI 的备用访问入口。

## 3. 功能

### 3.1 饮食记录相关功能

- **录入方式**（三种，互为补充）：
  1. **自然语言对话录入（主力）**：用户描述每餐食物、数量及生熟状态，LLM 将普通食物归一为克重，将已命中的个人固定食谱归一为份数，系统据此计算热量与四大营养素。“清蒸/油炸/红烧”等做法保留在食物名称中，不另设制备方式字段。
  2. **照片估算录入**：用户预先在「我的」录入自己握拳的长/宽/高作为参照尺寸，拍照时将拳头一并入镜；LLM 以拳头为比例参照推测食物种类、生熟与克重，并将判断依据用自然语言播报给用户确认（如「照片里是三文鱼寿司和红烧肉，其中三文鱼大概生重100g……」），用户可在确认前修正。
  3. **手动录入**：LLM 不可用、解析失败或用户希望直接填写时，可手动输入食物、餐次，以及普通食物的克重和生熟状态或既有个人食谱的份数；系统仍执行同一四级查询。查询未解析时不生成业务记录；LLM 可用则回到聊天继续追问，不可用则明确提示未解析，均不提供手填营养入口。
- **常吃食物永久复用**：常吃食物的单位只有克或份，`preparation_state` 只有生、熟、食谱三种。生/熟食物按克复用且没有组成；固定食谱按份复用，只有食谱保存一份固定配方中各组成项的克重和生熟状态。何时提示保存仍由 SPEC §7 的统一路径维护。
- **食物数据源**：LLM 负责识别食物名称（含做法语义）、数量、生熟状态并把普通份量描述估算为克重，不负责给出营养数值——营养值采用四级查询链「个人常吃库 → 中国第六版 GitHub OCR 数据 → USDA FoodData Central → 网络搜索估算」，避免 LLM 记忆漂移；非权威来源的数据标注来源并提示用户确认（详见 §5.1）。
- **确认策略**：每一级食物库都可能返回多个相似候选；单一兼容项直接采用，多候选先由 LLM 从候选集合中选择语义上明确的日常常见项，没有明确常见项时才交给用户选择。第①–③级由 LLM 明确选出的常见项可直接写入并提供撤销/编辑；照片估算、用户候选选择、网络估算、历史补录/修改，以及运动/身体数据对话录入仍须 Confirm。
- **今日餐次明细表**：以表格形式展示当天三餐 + 加餐的每项食物及其 kcal / 四大营养素，数据来自短期库，支持编辑（改数量按比例缩放）与删除。
- **每日摄入趋势图**：上下联动两张图，共享同一时间窗口——上图为每日摄入热量柱状图（叠加运动消耗，见 3.2）；下图为每日四大营养素堆积柱状图（绝对克数）。数据来自长期库。
- **数据生命周期**：短期库只保留最近 7 个归属日明细，长期库永久保留每日汇总；本地时间凌晨 2:00 为归属日分界。最近 7 日可通过对话或手动方式补录/修改：业务今日保持实时聚合，已结束日期在确认后原子重算汇总并保留原 BMR 快照。
- **对话历史管理**：记录 Tab 内的对话历史保留最近 7 个归属日，与短期库同生命周期、一并清理；清理只影响对话气泡本身，不影响任何已落库的结构化数据（餐次记录、汇总、常吃食物库）。

### 3.2 运动记录相关功能

- **录入方式与未来探索**：
  1. **手动录入（当前实现）**：在「看板」Tab 的独立表单中录入运动类型（有氧/力量/核心/其他）、时长、消耗 kcal。
  2. **对话录入（规划中）**：用户口述运动情况，LLM 解析为与手动表单一致的字段（类型/时长/消耗 kcal）后写入，无需切换到表单填写，解析 schema 与手动录入共用（见 §5.2）。
  3. **手表/穿戴设备自动同步（不在当前路线图）**：纯 PWA 不承诺直接读取 Apple Health、Health Connect 或通用手表数据。未来只有确认具体厂商 Web API 可用后才另行立项，当前功能与里程碑均不依赖此能力。
- **消耗可视化**：在长期摄入趋势柱状图中，每日一根柱子——橙色为当日摄入热量，灰色从柱顶向下扣减代表运动消耗，肉眼可见橙色高度即为「摄入净剩」；柱顶小字显示当日等效摄入与碳水:蛋白:脂肪比例。保留柱子总高度等于摄入的原始设计；异常出现运动消耗大于摄入时，灰色高度取 `min(运动消耗, 摄入)`，橙色可见高度与等效摄入均取 `max(摄入 − 运动消耗, 0)`。

### 3.3 身体数据记录相关功能

- **基础信息**：性别、身高、年龄（在「我的」录入）。
- **身体维度**：体重、体脂率、腰围、臀围、大腿围、小腿围，各字段可选填，记录间隔不固定（凭心情录入）。支持两种录入方式：「我的」Tab 表单手动录入（当前实现）；与 LLM 对话描述（规划中，如「今天体重70.2公斤」），由 LLM 解析为与手动表单一致的字段后写入，两者共用同一套 schema 与校验逻辑。
- **握拳尺寸**：长/宽/高，供饮食照片估算使用。
- **BMR 自动计算**：根据个人信息自动计算并显示，用于每日总消耗（BMR × 1.2 + 活动消耗）、热量 Δ 与建议热量缺口。默认在存在体脂率数据时优先使用 Katch-McArdle 公式（基于瘦体重），否则使用 Mifflin-St Jeor 公式；提供「体脂率优先」开关（默认开启，关闭后恒用 Mifflin-St Jeor），公式发生切换时通过悬浮提示告知用户。
- **减脂计划**：在「看板」Tab 设定目标体重与目标达成日期，系统据此推导合理的周减重速度与每日建议热量缺口（不由用户直接填写周减重速度）。
- **身体维度趋势图**：可勾选体重/体脂率/腰围/臀围/大腿围/小腿围多条折线，支持切换多档历史时间窗口（具体档位见 SPEC）；因记录间隔不固定，X 轴按窗口内记录数等间距排列（非真实时间轴），悬浮显示真实日期与数值；缺测的维度在该点做跳连处理；数据点按相对上次记录的变化趋势染色（绿降/蓝平/橙升）。

## 4. 用户体验

### 4.1 主要使用模式

- **日常记录（高频、轻量）**：用户在「记录」Tab 与 LLM 对话录入三餐/加餐，今日明细实时同步反馈，形成紧凑的「录入 → 反馈」闭环，单次操作应在几句对话内完成。
- **定期复盘（低频、深度）**：用户前往「看板」Tab 查看摄入趋势、运动消耗叠加、身体维度变化与减脂计划进度，做整体判断而非纠结单日波动。
- **偶尔维护（低频、设置类）**：在「我的」Tab 更新基础信息与身体维度数据，或调整 BMR 计算方式。

### 4.2 页面结构

采用面向手机竖屏的多 Tab 单列结构，而非单页可拖动组件。组件只定义职责和切换关系，不规定宽屏左右布局；电脑浏览器沿用同一手机 UI，不另做宽屏专属页面。

- **Tab 1 · 记录（每日交互中心）**：包含 LLM 对话录入（文本/图片）、今日餐次明细和常吃食物库三个功能组件；组件之间的具体呈现和切换方式由 UI 设计决定。
- **Tab 2 · 看板（复盘中心）**：每日摄入趋势图（热量+营养素堆积双联动子图）、运动记录录入表单、减脂计划组件（目标进度圆盘图 + 计划周期体重曲线，含「设置计划」入口）、身体维度折线图（时间窗口 + 多维度勾选）。
- **Tab 3 · 我的（设置中心）**：基础信息与身体维度录入、握拳尺寸录入、BMR 计算结果与公式切换说明。目标体重/达成日期的设定统一收敛在「看板」Tab 的减脂计划组件中，避免同一决策分散在两个 Tab。

## 5. 技术需求

### 5.1 数据架构

- **短期库（餐次明细）**：仅保留最近 7 天的逐项食物记录（含 kcal 与四大营养素），驱动「今日餐次明细表」；由每日结转任务清理超期数据。
- **长期库（每日汇总）**：永久保存每日总 kcal 与四大营养素总量，驱动「每日摄入趋势图」；结转时写入当日 BMR 快照，保证历史 Δ 计算不随后续 BMR 变化而漂移。
- **每日结转任务**：定时将短期库当日明细加总写入长期库，并清理短期库中超过 7 天的数据；跨天以本地时间凌晨 2:00 为界；仅允许对短期库仍保留的最近 7 天数据补录/修改，超期数据因明细已清理无法反推，只能保留长期库汇总。
- **食物数据源**：基础数据分为本地导入的中国第六版 GitHub OCR 数据与 USDA FoodData Central，不混成一张通用表；核心文档只规定两个来源不同的计算注意点，不复制完整字段。查询按「个人常吃库 → 中国食物数据 → USDA FoodData Central → 网络搜索估算」四级链执行。中国营养值按每 100g 可食部提供，只有输入为带壳/带骨等总重时才乘可食率；USDA 数据由适配器按来源口径规范化为每 100g 候选。外部来源的原生份量不成为业务依赖，只有个人固定食谱永久使用“份”。
- **身体维度库**：永久保存，各字段独立缺测跳连；由于录入间隔不固定，图表展示与真实时间解耦（等间距 + 悬浮真实日期）。
- **对话历史库**：仅保留最近 7 天，与短期库同生命周期，和结构化数据（餐次/汇总/常吃食物）完全解耦，清理对话不影响任何已入库的业务数据。

### 5.2 LLM 对话窗口

对话组件是饮食录入的主入口，需要支撑以下能力：

- 自然语言饮食解析（食物 + 数量 + 克/份 + 生熟/食谱 + 餐次）；普通食物的碗、个、盘等描述由 LLM 在本次解析中估算为克重，信息不足时追问而不是编造营养值。
- 照片估算解析：结合握拳参照物判断食物种类、生熟与克重区间，必须给出置信度与理由，并用自然语言向用户播报判断依据，确保用户在确认/微调前已理解 LLM 的推理过程。
- 补录/修改对话：基于目标日现有明细，以增删改操作的形式让用户确认后执行。
- 常吃食物库的对话式维护（新增/更新/删除自制菜品与固定搭配）。
- **运动与身体数据的对话式录入（规划中，见 §9）**：对话窗口不再局限于饮食，用户也可口述运动情况或身体维度数据，LLM 解析为与各自手动录入表单一致的结构化字段（运动：类型/时长/消耗 kcal；身体数据：体重/体脂率/腰围/臀围/大腿围/小腿围）后写入，复用同一套 schema 与写入校验逻辑，不额外维护第二套数据结构。
- **输出契约**：全部要求严格 JSON 输出，解析失败时以追问方式回退；LLM 负责饮食识别、生熟判断和在系统返回的候选集合内做语义消歧，不生成候选之外的食物或营养值。具体营养计算与校验统一由系统负责。

### 5.3 LLM API 的性能与成本要求

- **模型选型方向**：选择支持中文、多图和可靠结构化输出的多模态模型；Qwen3-VL 系列可作为候选，但具体版本、供应商和价格属于易变的实现决策，由独立 ADR/配置维护。
- **部署方式**：先以云 API 起步，后续按需评估自托管（仅自托管场景涉及 GPU 成本）；后端应做供应商无关封装，便于切换模型或做 A/B 对比，降低对单一供应商的依赖。
- **性能要求（待细化）**：当前文档尚未定义对话解析/照片估算的响应时间 SLA，建议在后续 Spec 中结合实际录入体验补充明确指标（如「文本解析 P95 ≤ N 秒」），并作为验收依据之一（见第 7 章）。
- **失败降级**：查询失败或限流时自动进入下一级数据源；四级查询仍无法解析且 LLM 可用时，由 LLM 在聊天中继续追问用户。手动录入始终可用，但不承担手填营养功能；在获得可信营养结果前不写入正式餐次，也不另建未提交草稿。

### 5.4 平台支持

- **主要终端**：以手机竖屏为主要使用环境，交付可添加到主屏幕的 PWA；不开发 iOS/Android 原生 App，也不以应用商店发布为目标。
- **电脑访问**：允许在现代电脑浏览器中打开同一 PWA，但只要求功能可用，不提供宽屏专属布局或另一套桌面组件结构。
- **数据位置**：所有终端访问同一个单用户私有后端和同一份业务数据，不设计本机数据库之间的同步，也不提供公开注册、多人账号或用户切换。
- **联网边界**：安装后的 PWA 不等于完整离线应用。读取和写入业务数据、LLM、USDA 及网络搜索均依赖私有后端或外部网络；断网时应明确提示不可提交，不承诺离线写入后再同步。
- **穿戴边界**：当前路线图不承诺 Apple Health、Health Connect 或通用手表自动同步。只有未来确认某一设备厂商提供适合私有 Web 服务使用的 API 后，才单独立项评估；不得以此重新引入原生 App。

## 6. 非功能性需求

- **隐私与安全**：业务数据持久化在单用户私有后端，后端不提供公开注册或匿名访问；完成 LLM 解析、USDA 查询与网络搜索时，必要的文本、图片或食物查询词会发送给对应第三方处理。当前不做远程分析上报；所选供应商应支持关闭训练或采用满足要求的数据保留策略，API Key 仅由私有后端安全持有。出网披露、访问保护、密钥保护和供应商保留要求必须在 MVP 前明确。
- **可用性/容错**：LLM、USDA、网络搜索任一环节失败时依次降级；四级查询仍无法解析时回到聊天追问，也可切换到结构化手动录入。缺少可信营养结果时不写入正式餐次、不创建未提交草稿，也不能用虚构营养值完成记录。
- **数据一致性**：短期库与长期库之间通过「即时重算 + 幂等结转」保持一致，避免补录/编辑后出现汇总与明细对不上的情况。
- **可备份性**：需支持导出和恢复一个完整备份产物；若短期聊天图片不在 SQLite 内，备份产物应是包含数据库和保留期图片的归档包。历史趋势是核心价值，不能只做导出而没有恢复路径。
- **性能**：面向单用户、数据量小的场景，趋势类查询应基于已聚合的长期库数据，达到无感知延迟；具体 P95 指标由实现前的验收配置定义。
- **兼容性**：优先保证主流 iOS Safari 与 Android Chrome 的手机竖屏浏览和添加到主屏幕体验；现代电脑浏览器只需正确显示并可操作同一手机 UI，不验收宽屏专属适配。

## 7. 测试需求

> 本产品此前未定义测试计划，以下为基于现有功能梳理提出的建议范围，供后续 Spec/开发阶段细化用例。

### 7.1 单元测试

- 计算引擎：BMR 双公式（Mifflin-St Jeor / Katch-McArdle）计算正确性与切换判定；每日总消耗与热量 Δ；减脂计划派生量（周期天数、目标差值、日均缺口、周减重估算）；营养素三项比例归一化。
- 数据换算：按新旧数量比例缩放 kcal/营养素；生熟重口径匹配（避免生重表被误用于熟重食物）。
- 归属日与结转：本地时间凌晨 2:00 边界的归属日判定；7 天保留窗口的清理边界；结转幂等性（重复触发不重复累加）。

### 7.2 集成测试

- 食物四级查询链路：逐级召回单个或多个候选，无候选才降到下一级；覆盖 LLM 选择明确常见项、无明确常见项时用户选择、“都不是”后继续降级、普通食物克重归一及固定食谱按份复用。
- LLM 契约：自然语言解析、照片估算、补录对话、常吃库增删改各类 JSON 契约的结构校验与异常回退（信息不足触发追问、重名冲突提示）。
- 数据联动：明细编辑/删除后已结束归属日的汇总是否在同一事务内同步重算；身体维度补录后各计算是否仍读取按日期最近一次非空测量；减脂计划新建与已有计划重叠时的合并/截断处理。
- 结转任务全链路：定时触发 → 聚合 → 清库 → 补跑判定，覆盖「漏跑后重新启动」等异常场景。

### 7.3 验收测试（用户视角端到端场景）

- 对话录入一餐 → 明细表实时更新 → 趋势图数据同步正确。
- 拍照估算（含/不含握拳参照物）→ LLM 播报识别结果 → 用户微调 → 确认后正确落库。
- 对 7 天内某天进行补录/修改 → 明细与汇总一致更新 → 自动退出补录模式。
- 录入运动记录后，趋势图灰色遮盖高度与柱顶等效摄入数值符合预期。
- 是否录入体脂率会正确影响 BMR 计算公式与悬浮提示文案。
- 减脂计划全流程：新建 → 查看进度圆盘/曲线 → 设置冲突计划触发合并或截断选择。
- 身体维度图表：多维度勾选、时间窗口切换、缺测跳连、趋势染色均符合预期。
- 边界场景：超过 7 天的明细不可再补录/编辑；清理对话历史不影响任何已落库数据。
- PWA 可从支持的手机浏览器添加到主屏幕并独立启动；电脑浏览器显示同一组件结构，且不存在必须依赖宽屏布局才能完成的功能。
- 私有后端不可达时清楚提示联网失败，不接受看似成功但尚未持久化的业务写入。

### 7.4 验证指标（建议）

- LLM 输出结构合法率（JSON 校验通过率）达到较高阈值，低于阈值需触发追问而非静默失败。
- 食物四级查询命中率分布（各级占比），用于评估本地数据源覆盖度是否需要扩充。
- 照片估算克重与用户最终确认克重的平均偏差，按置信度分级分别统计，验证置信度提示是否可信。
- 每日结转任务成功率与补跑准确率要求达到 100%，不允许长期库出现脏数据。
- 短期库与长期库一致性抽样校验：聚合结果与逐行求和结果误差应为 0。
- 关键交互响应时间（如明细编辑保存、趋势图加载）作为体验类指标持续观测。

## 8. 依赖性和限制

**外部依赖**：

- LLM 多模态服务（如 Qwen3-VL 系列）：依赖网络可用性、API 配额与调用成本，是产品可用性的单点风险。
- USDA FoodData Central REST API：需要 API Key，并按官方当前限流规则处理缓存与降级；不在 PRD 固定易变化的额度数字。
- 中国食物成分数据：自用阶段采用公开 GitHub 仓库 `Sanotsu/china-food-composition-data` 的第六版 OCR/视觉识别结果并本地固定版本。仓库作者明确提示识别准确率不保证、原始内容版权归原作者，且当前未展示明确开源许可证；对外测试或分发前必须重新确认授权和数据质量，不能因仓库公开就默认可以再分发。
- 网络搜索兜底：结果质量不可控，仅作为最后一级兜底并明确标注「可能不准」。

**产品与技术限制**：

- 本产品采用单用户私有后端，不含公开注册、多用户账号、用户切换或按用户隔离的数据模型；业务表不保留 `user_id` 占位字段。若未来转为多人产品，账号、授权和数据归属必须作为新的产品阶段整体设计。
- 短期库仅保留 7 天明细，超期数据不可逆——长期库只存汇总、无法反推明细，因此补录窗口硬性限制在 7 天内。
- 归属日按本地设备时间计算、不做时区回溯，跨时区或更换设备场景下的边界一致性尚未处理。
- 当前路线图中的运动消耗仅支持手动/对话录入；纯 PWA 不承诺直接读取 Apple Health、Health Connect 或通用手表数据，厂商 Web API 接入只作为未来独立探索项。
- 照片估算精度受限于 2D 图像缺乏深度信息，依赖参照物（握拳尺寸）与用户人工微调，无法做到与称重同等精度。
- 不设计游戏化或社交监督机制，产品坚持度依赖用户自我驱动；不做展示型分享功能。

| 运动记录功能需求 | 保持手动与对话录入。通用穿戴同步不属于本阶段承诺；只有已确认可用的设备厂商 Web API 才可另行立项。 |
| 身体数据功能需求 | 保持手动和对话录入，所有授权终端读取同一份身体趋势、BMR 与减脂计划。 |
| LLM 对话功能需求 | 三类对话在 PWA 中稳定支持文字、拍照、确认、追问和服务不可用提示。 |
| 阶段完成标志 | 用户可以在手机上长期稳定使用已安装 PWA，私有后端、升级和备份恢复没有阻断性问题。 |

### 9.5 Stable — 个人正式版与长期维护

| 维度 | 本阶段范围 |
| ---- | ---------- |
| 阶段目标 | 全量能力达到个人正式使用标准，进入可持续维护状态，不面向公众开放。 |
| 平台 | 手机 UI PWA + 单用户私有后端；不发布原生 App，不提供宽屏专属版本。 |
| 页面结构与组件 | 三 Tab、加载/空状态/错误恢复、隐私告知、私有访问状态和备份恢复入口完整稳定。 |
| 数据功能需求 | 同一份私有数据在本人的授权设备上保持一致；支持可靠的备份、恢复和版本升级，历史记录不会静默丢失。 |
| 饮食记录功能需求 | 文本、照片、手动录入、四级查询、常吃食谱、补录编辑和趋势复盘稳定可用。 |
| 运动记录功能需求 | 手动与对话录入稳定并存，运动消耗结果可信；穿戴设备接入不作为正式版完成条件。 |
| 身体数据功能需求 | 手动、对话、趋势、BMR 和减脂计划稳定可用。 |
| LLM 对话功能需求 | 饮食、运动和身体数据的统一对话稳定可用；用户能理解何时需要确认、何时需要补充信息，以及服务不可用时会发生什么。 |
| 阶段完成标志 | 全量功能和第 6 章非功能性需求达到个人正式使用标准。 |

**阶段划分依据**：

- Demo 只验证饮食文本录入与趋势价值，不提前引入照片、运动、身体数据和常吃库等变量。
- MVP 先让饮食、运动、身体数据各自形成完整功能闭环，再在 Closed Beta 将运动和身体数据接入统一对话。
- PWA 手机形态从 Demo 起就是产品本体，Release Candidate 只增强安装、私有访问、升级与备份恢复的稳定性，不再另开移动端工程。
- 手动录入和专用组件在引入对话后仍保留，作为用户可直接控制的录入方式。
- 通用穿戴同步、多人账号、公众注册、宽屏专属界面和原生 App 均不属于当前路线图；未来若改变方向，必须先重新修订 PRD。
