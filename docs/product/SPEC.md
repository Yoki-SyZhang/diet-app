# 减脂软件 · 技术规格说明书 (SPEC)

**输入依据**：《减脂软件 · 产品需求文档 (PRD)》v2.15
**版本**：v2.9（统一为手机 UI PWA + 单用户私有后端；删除多用户占位并重构后期里程碑）
**范围**：本文档设计 PRD §9 中 Demo / MVP / Closed Beta / Release Candidate / Stable 的单用户私有 PWA。手机是主要终端；电脑浏览器只复用同一手机 UI，不做宽屏专属适配，也不开发原生 App。

**SPEC 编写原则：**

- SPEC 聚焦系统设计，而非实现细节。描述架构、接口、数据模型、业务逻辑、状态流转与技术约束。
- 验收说明只保留验收标准（Acceptance Criteria）。不包含完整测试用例、QA 测试计划、CI 工作流、埋点/分析细节，或实现层面的 TODO。
- 每个章节保持在「设计决策」层面，而非「执行细节」层面。

---

## 1. 技术架构

系统采用“可安装的手机 UI PWA + 单用户私有后端”结构。业务数据持久化在私有后端的 SQLite；PWA、后端 API、LLM、USDA 和第④级网络搜索均依赖网络连接。系统不提供公开注册或多人账号。

```
前端 (React + TypeScript, PWA)
  ├ 记录 Tab   对话录入 + 今日明细/常吃食物库
  ├ 看板 Tab   摄入趋势图 + 今日热量详情 + 身体折线 + 计划组件 + 运动录入
  └ 我的 Tab   个人信息 + 身体维度 + BMR
        │ HTTPS 私有 API
单用户私有后端 (Python + FastAPI)
  └ LLM 编排 / 食物四级查询 / 计算引擎 / 结转任务
        │
   SQLite（私有后端单文件）
        │
   多模态 LLM 适配器 / USDA REST / 网络搜索 / 本地中国 OCR 数据快照
```

**当前系统边界**：通过安全上下文交付的可安装 PWA + 仅允许本人授权终端访问的私有后端 + 后端 SQLite 单文件。私有后端可以位于个人设备或私有服务器，但其访问边界必须独立于业务数据模型；系统不建立账号、用户切换或按用户隔离逻辑。React/TypeScript、FastAPI、SQLite 与 ECharts 是当前首选技术栈；具体库、REST 路径命名、数据库语法和私有接入方式可在不改变本文业务契约的前提下调整。

PWA 以手机竖屏为唯一正式布局目标，并支持添加到主屏幕。电脑浏览器可访问同一应用，但复用手机组件结构，不增加宽屏断点、左右分栏或桌面专属页面。原生 iOS/Android App、桌面壳及应用商店发布均不在路线图内。

## 2. 页面结构与组件

采用面向手机竖屏的多 Tab 单列结构。各组件只定义职责和交互关系，不绑定左右位置；电脑浏览器沿用同一结构，不做宽屏专属适配。各组件与数据库的读/写对应关系汇总见 §3。

### 2.1 Tab 1 · 记录（每日交互中心）

**A · 对话录入组件**：提供文本 + 图片上传（支持俯拍/侧拍多图），用于录入饮食、发起补录、维护自制菜品；用户也可切换到结构化手动录入表单。全部食物查询、确认、写入和常吃库维护路径统一见 §7。

  - **范围（里程碑）**：MVP 阶段对话只解析饮食；Closed Beta 起扩展到运动、身体数据（§8.6/§8.7），Confirm 后复用对应手动表单的业务服务与校验，不维护第二套写入逻辑。

**B · 今日明细组件**（读写 `meal_entry`）：

- 按餐次展示食物名称、数量、热量与四项营养素，并显示餐次小计和全天汇总；清蒸、油炸、红烧等做法直接体现在食物名称中，具体列布局和行操作形式留给 UI 实现。
- 已写入行支持修改数量和删除。同一单位下只修改数量时，按该条目的营养快照等比例重算，不重新调用 LLM；单位变化按 §7 重新解析和查询。`meal_entry` 保存录入时的营养快照，之后修改常吃库不回溯历史。
- 第④级网络估算及其后续常吃库复用始终显示「可能不准」。
- **里程碑范围**：本节描述的表格内手动编辑/删除能力为 **MVP 起** 支持；**Demo 阶段今日明细表仅只读展示**，修正/删除只能通过与 LLM 对话完成（§6.2/§8.3 补录契约，7 天窗口内含当天）。

默认显示今日；补录模式下展示目标日的“现有数据 + 待确认变更”预览，Confirm 后才在同一事务内写回并自动跳回今日（§6.2、§7）。

**C · 常吃食物库组件**（读 `food_favorite`）：展示名称、`preparation_state`、g/serving、标准营养、食谱组成摘要和来源可信度，支持搜索、排序与删除。展示细节及组件之间的切换或组合方式由 UI 设计决定；查询、增加、更新、相似项处理和删除的唯一业务定义见 §7。

- **里程碑范围**：本表与常吃库维护均为 **MVP 起** 支持；Demo 阶段跳过第①级常吃库，从本地中国第六版 OCR 数据开始查询。

### 2.2 Tab 2 · 看板（复盘中心）

**A · 每日摄入趋势图**（读 `daily_summary` + `exercise_entry`）：由两个联动子图组成，共享同一时间窗口选择器与「今日口径」规则。

**A1 · 热量柱状图**：保留原始设计。每日一柱，橙色=当日摄入热量 (kcal)、灰色（柱顶下扣）=当日运动消耗；柱子总高度始终等于当日摄入。灰色可见高度为 `min(activity_kcal, total_kcal)`，剩余橙色可见高度与柱顶“当日等效摄入”均为 `max(total_kcal - activity_kcal, 0)`，从而在异常边界下不越过柱底；另一行小字显示 `碳水:蛋白:脂肪` 比例。

**A2 · 营养素堆积柱状图**：每日一柱，按碳水/蛋白质/脂肪/膳食纤维四色堆积展示当日摄入的绝对克数 (g)，Y 轴为克数。

- **时间窗口**：A1/A2 共用同一时间窗口选择器，均为滚动窗口（不跟随自然周/月边界）：默认显示过去 7 天，可切换过去 14 天 / 过去 30 天；切换时两图同步刷新。
- 「今天」尚未结转（无 `daily_summary`），A1/A2 当日柱由短期库 `meal_entry` 实时聚合，运动消耗由 `exercise_entry` 实时聚合；次日结转后改读长期汇总。
- 没有正式饮食数据的日期表示“缺失记录”，两张图均不画该日柱子，不以 0 摄入代替。

**B · 今日热量详情卡**（读实时 `meal_entry` + `exercise_entry` + `user_profile` + `body_metric`(BMR) + `diet_plan`）：单卡集中展示当天

| 指标         | 值                                                |
| ------------ | ------------------------------------------------- |
| 今日摄入     | total_kcal                                        |
| BMR          | 当前 BMR                                          |
| 活动消耗     | activity_kcal                                     |
| 今日 Δ      | total_kcal − BMR × 1.2 − activity_kcal         |
| 今日目标 Δ  | −建议日缺口（有计划按 §5.3 推导；无计划 −200） |
| 各营养素摄入 | 碳水 / 蛋白 / 脂肪 / 纤维 (g)                     |
| 营养素比例   | 碳水:蛋白:脂肪                                    |

用于直观对照「今日 Δ vs 目标 Δ」，判断当天是否达标。

**C · 身体维度折线图**（读 `body_metric`）：

- 时间维度：过去 1 月 / 过去 3 月 / 过去半年 / 过去 1 年四档。
- 身体维度多选（体重/体脂率/腰围/臀围/大腿围/小腿围），各成独立折线，按 kg、%、cm 使用单位一致的刻度；具体轴分配由图表实现决定。
- X 轴按记录等间距（非真实时间轴），标签显示记录日期；悬浮显示数值。
- 趋势染色（相对上一有值点）：绿=下降，蓝=处于单位相应的容差内，橙=上升。各单位的精确容差放在可调整的验收配置中，不写死在核心 SPEC。
- 缺测跳连：某维度缺测点，该折线直接连接前后有值点。

**D · 减脂计划组件**（读 `diet_plan` + `body_metric`；写 `diet_plan` + `body_metric`）：

- **展示态**：读取 `diet_plan` 中 `is_active = 1`（`start_date ≤ 今日 ≤ end_date`）的计划：

  - **图1 目标圆盘图**：展示初始体重、目标体重、当前体重；完成度 `= (start_weight − current) / (start_weight − target_weight) × 100%`。
  - **图2 计划周期体重折线图**：X 轴为真实时间等距（与 C 不同）。两条序列：① 半透明理论指数下降曲线 `W(t) = target + (start − target)·e^(−k·τ)`，`τ = (t − start)/(end − start)`，`k≈3`（仅参考形状）；② 真实体重折线（计划期内实测点，按真实日期落位）。此图只服务计划。
  - 无生效计划（`diet_plan` 为空或所有记录 `is_active = 0`）时，图1/图2 版面显示「当前无计划」。
- **设置计划按钮**：组件固定提供「设置计划」入口按钮，**无论当前有无生效计划，点击后弹出的设置弹窗是同一个、行为完全一致**——不区分"新建"与"修改"两种模式，每次提交都视为设置一个新的计划意图，若与既有计划重叠再触发合并/截断二次确认（见下）：

  - **开始日期**：日期选择，默认今日；写入 `diet_plan.start_date`。
  - **初始体重**：数值输入，默认带入 `body_metric` 中按日期最近一次非空体重，允许用户修改；提交时若不同，先 upsert 一条 `date = 今日` 的体重记录，再以此值作为新计划的 `diet_plan.start_weight`。
  - **目标体重**：数值输入，默认 = 初始体重 − 1kg；写入 `diet_plan.target_weight`。
  - **结束日期**：日期选择，默认今日 + 30 天；写入 `diet_plan.end_date`；**校验：不允许 `end_date ≤ 今日`，且不允许 `end_date ≤ start_date`**，否则提交按钮禁用/报错提示。
  - **实时预览小字**：以上任一字段变化时实时刷新——「当前计划每周预计体重下降 X kg，每日热量缺口 −X kcal」（按 §5.3 公式）。MVP 不做激进程度提示；是否增加提醒或限制列为 Closed Beta 产品决策。
  - **唯一生效约束与重叠处理**：同一时间只允许一个生效计划。点击确认后，检测本次设置的日期区间是否与**当前生效计划**（`is_active` 判定见 4.8，即 `start_date ≤ 今日 ≤ end_date` 的那一条）重叠——本弹窗「开始日期」默认今日，新计划不会与已结束的历史计划产生重叠，故重叠检测范围限定为当前生效计划即可，无需扫描全部历史记录。若重叠，弹出二次确认，提示用户二选一：

    - **合并**：将两者合并为一个计划，取更早的 `start_date` 与更晚的 `end_date`，`start_weight` 沿用 `start_date` 更早的那个计划原有的 `start_weight`（保留最初起点基准）；
    - **截断旧计划**：将旧计划的 `end_date` 改为新计划 `start_date` 的前一天。

    无重叠时直接写入一条新 `diet_plan` 记录。
  - 弹窗提交后写入 `diet_plan`；只有初始体重被用户修改时才按上文额外写入 `body_metric`。

**E · 运动录入组件**（读写 `exercise_entry`）：

- 选择 `category`：有氧 / 力量 / 核心 / 其他。
- 输入 `duration_min` 与 `kcal_burned`。
- 列出当日已录运动，每行按 `source_tag` 显示来源小标（手动/对话，见 §4.3）；可继续添加。
- 空态：一行提示「今天还没有运动记录哦」。
- **里程碑范围**：MVP 仅支持本组件手动录入（`source_tag = manual`）；Closed Beta 起同一张表还接收对话录入产生的记录（`source_tag = dialogue`，见 §8.6）。当前数据模型不预留穿戴来源；未来厂商 Web API 若单独立项，再同步修订数据模型。

**今日口径**：今天尚未结转、无 `daily_summary`，柱状图当日柱与今日热量详情卡均由短期库 `meal_entry` 实时聚合，BMR 取当前值（无快照）；次日 02:00 结转后转为长期库口径。

### 2.3 Tab 3 · 我的（设置中心）

「我的」的 A/B 两个组件均采用“只读展示 + 编辑”模式：平时显示当前值，时序字段按各字段日期分别读取最近一次非空实测；这里是身体数据的主要手动输入入口，减脂计划与 Closed Beta 对话录入可复用同一写入规则。

**A · 基础信息录入组件 :**

- 性别、身高、年龄、握拳尺寸录入。

**B · 身体维度录入组件** :

提供日期选择器（默认今日，可回选过去日期补录）+ 体重/体脂率/腰围/臀围/大腿围/小腿围六个数值输入（均可空，只填其中若干项）。提交时按所选 `date` upsert 到 `body_metric`；历史补录不会覆盖比它日期更晚的“当前值”，读取方始终按字段查询最近一次非空测量。

- 当前体重、体脂率（UI 百分数，存小数 0–1）。BMR 自动计算显示（含公式切换悬浮注释）；提供「体脂率优先」开关（`user_profile.use_bodyfat_bmr`），默认开启，关闭后恒用 Mifflin-St Jeor 公式（见 §5.1）。
- 其他身体维度录入（同日期覆盖更新）。

**首次使用引导**：BMR 与减脂计划组件（§2.2 D）依赖体重。用户尚未录入任何体重时，相关组件显示「请先在『我的』录入性别、身高、年龄、体重」，引导先录入这些基础信息再可使用。

## 4. 数据模型

单位：热量 kcal，营养素 g，长度 cm，重量 kg。`date` 为归属日（§6.1）；`created_at` 为 UTC-0 时间戳。

**单用户边界**：全部业务表只服务当前私有实例的唯一用户，不保存 `user_id`。私有后端的访问控制位于业务数据模型之外；若未来转为多人产品，必须重新设计身份、授权和数据归属，不能把当前单用户表直接视为已支持多用户。

### 4.1 短期库 · 餐次明细 `meal_entry`

保留最近 7 个归属日；结转任务清理。这里只保存本次归一后的数量、单位和营养快照，不保存食物库的 `preparation_state`、食谱组成或常吃库关联。字段名表达业务语义，具体 SQL 类型和自增策略由实现决定。

| 字段                                        | 说明                                                  |
| ------------------------------------------- | ----------------------------------------------------- |
| id                                          | 行标识                                                |
| date                                        | 归属日                                                |
| meal_slot                                   | breakfast/lunch/dinner/snack                          |
| food_name                                   | 用户确认后的食物名称                                  |
| quantity                                    | 本次计算使用的克数或份数                              |
| unit                                        | g 或 serving                                          |
| kcal / carb_g / protein_g / fat_g / fiber_g | 本次摄入营养快照                                      |
| source_tag                                  | 单一来源字段：chn_table/usda/web_estimate/user_create |
| created_at                                  | UTC-0 ISO8601 真实录入时刻                            |

`created_at` 以 UTC 存储，作为唯一真时间，即使用户所在时区变动也能溯源。归属日 `date` 仍按写入时的本地设备时间 −2h 计算并单独存字段；二者分工：`date` 管业务归属，`created_at` 管绝对时序与审计。

### 4.2 长期库 · 每日汇总 `daily_summary`（永久）

| 字段            | 类型      | 说明                                             |
| --------------- | --------- | ------------------------------------------------ |
| date            | TEXT      | 归属日，主键                                     |
| total_kcal      | REAL      | 当日热量汇总                                     |
| total_carb_g    | REAL      | 当日碳水汇总                                     |
| total_protein_g | REAL      | 当日蛋白质汇总                                   |
| total_fat_g     | REAL      | 当日脂肪汇总                                     |
| total_fiber_g   | REAL      | 当日膳食纤维汇总                                 |
| bmr_snapshot    | REAL NULL | 首次结转时的 BMR；资料不足时为空，之后重算不覆盖 |
| updated_at      | TEXT      | UTC-0，最后加总时间（审计用）                    |

主键：`date`。对每项聚合指标，只要当天任一已计入餐次的对应营养值为 null，该指标汇总也为 null，避免把未知误算成 0；因此热量柱和营养素柱可分别具有不同的完整性。

### 4.3 运动记录 `exercise_entry`（永久）

| 字段         | 类型       | 说明                                                                          |
| ------------ | ---------- | ----------------------------------------------------------------------------- |
| id           | INTEGER PK | 自增整数主键(`INTEGER PRIMARY KEY AUTOINCREMENT`),id 仅作行标识、无业务含义 |
| date         | TEXT       | 归属日                                                                        |
| category     | TEXT       | cardio/strength/core/other                                                    |
| duration_min | REAL       |                                                                               |
| kcal_burned  | REAL       |                                                                               |
| source_tag   | TEXT       | manual/dialogue，默认 manual                                                 |
| created_at   | TEXT       | UTC-0                                                                         |

`activity_kcal(date)` = 该归属日 `kcal_burned` 之和，不区分来源。

**路线图边界**：当前数据模型不包含穿戴同步来源。未来只有在设备厂商提供适合私有 Web 服务使用的 API 且另行立项后才扩展；届时须单独设计来源标识、授权、幂等和跨来源去重，不得以此为由引入原生 App。

### 4.4 外部食物基础库：`food_base_cn` / `food_base_us`

不再设置把两个外部来源改写成同一结构的 `food_base`。本地分别保存中国来源与 USDA 来源；本节只记录会影响查询和计算正确性的来源差异，不展开完整字段字典。查询适配器可在内存中生成 §7 使用的统一候选，但不得反过来要求两个来源拥有同名字段。

#### 4.4.1 中国来源 `food_base_cn`

本地导入 [Sanotsu/china-food-composition-data](https://github.com/Sanotsu/china-food-composition-data) 中第六版“能量和食物一般营养成分”的最新视觉识别结果，当前选用 `json_data_vision_251206_Qwen2-5-VL-72B-Instruct`。只投影本项目需要的食物标识、名称、可食率、kcal 和四项营养，不在 SPEC 复制仓库的完整 JSON 字段。

接入注意点：

- 仓库作者明确说明这是 OCR/视觉模型识别数据，准确率不保证，最新版约 1677 条且已移除字段结构不同的婴幼儿食品。导入必须固定到具体 commit，并对重复编码、缺失值、异常数值及可食率范围生成校验结果；不能在应用启动时静默拉取变化的 `main`。
- 数据中的营养值以每 100g 可食部为基准，`edible` 表示可食率百分比，不是“每份克重”。默认用户输入的 g 是实际吃下的可食部克重，直接按 `每100g值 × 可食部克重 / 100` 计算，不能再乘 `edible%`。
- 只有用户明确输入的是带壳、带骨或其他购入总重时，才先计算 `可食部克重 = 总重 × edible / 100`；输入口径不明时追问，不猜测。该口径是本次解析状态，不为 `meal_entry` 增加字段。
- `Tr`、破折号、空字符串、括号值等 OCR 原值不能统一转为 0；可确定为数值的才参与计算，其余按 §7.8 作为缺失或估计处理。
- 食物名可能包含生、熟、代表值、别名或做法描述。适配器保留完整名称，并在能够可靠判断时映射规范化生熟状态；清蒸、油炸、红烧等做法不再拆成独立字段，歧义时让用户确认。
- 中国源不承担“碗/个/盘 → 克重”的业务换算；除个人固定食谱外，所有输入在查询前归一为克重。
- 该仓库虽公开可访问，但 README 写明 OCR 不保证一致且原始内容版权归原作者，仓库当前也未展示明确的开源许可证。当前自用阶段可作为数据源方案推进；进入对外测试或分发前必须重新确认授权，不能把“公开 GitHub 仓库”直接等同于可再分发的开放数据。

#### 4.4.2 USDA 来源 `food_base_us`

USDA 表缓存 [FoodData Central Food Details API](https://fdc.nal.usda.gov/api-guide/) 的最小投影，只保留查询和五项营养规范化所需内容，不在 SPEC 展开完整响应字段。

接入注意点：

- 营养数据是数组，必须按官方 nutrient ID 并同时校验名称和单位，不能按数组位置取值；不同 `dataType` 的能量 ID 不完全相同，同一记录出现多个能量值时按适配器的单一优先级选择，不能相加。
- USDA 记录也可能缺少某项营养；缺失保持 null，不用 0 补齐，也不因为缺一项就改用数组中名称近似但定义不同的营养。
- USDA 不同 `dataType` 的营养口径可能不同，适配器须依据官方字段说明生成每 100g 候选；来源自带的份量信息不作为本系统的持久业务模型，也不套用中国数据的 `edible%`。
- raw/cooked 等信息通常包含在 `description` 文本中。适配器保留完整名称，并只在可靠时映射规范化生熟状态；不建立统一的制备方式枚举，多候选或描述不清时仍按 §7 追问/确认。
- API 结果按 `fdcId` 缓存并保留 `dataType`，同时遵守 API Key、限流和失败降级规则。详细字段事实以 USDA [OpenAPI](https://fdc.nal.usda.gov/api-spec/fdc_api.html) 与 [Download Field Descriptions](https://fdc.nal.usda.gov/docs/Download_Field_Descriptions_Oct2020.pdf) 为准，不复制进核心 SPEC。

长期库 `daily_summary` 只有聚合结果，不重复保存任何外部单项食物字段。

## 5. 计算引擎

### 5.1 BMR

BMR 使用 `user_profile` 的基础信息，并从 `body_metric` 分别读取按日期最近一次非空的体重和体脂率：

- `use_bodyfat_bmr = 0`（开关关闭）→ 恒用 Mifflin-St Jeor：男 `10w + 6.25h − 5a + 5`；女 `10w + 6.25h − 5a − 161`。
- `use_bodyfat_bmr = 1`（默认开启）：
  - 最近体脂率为空 → 同上，用 Mifflin-St Jeor。
  - 最近体脂率非空 → Katch-McArdle：`LBM = w × (1 − bf)`，`BMR = 370 + 21.6 × LBM`。体重和体脂率各自取最近一次非空值，不要求来自同一日期。

### 5.2 每日总消耗与热量 Δ（不引入活动系数）

`当日总消耗 = BMR × 1.2 + activity_kcal`；`Δ = total_kcal − BMR × 1.2 − activity_kcal`。BMR 采用当日 `bmr_snapshot`，历史 Δ 不漂移。Δ < 0 为赤字（减脂方向）。

* 固定 1.2 代表"久坐日常生活基线"(NEAT + TEF),运动单独记 `activity_kcal` 叠加,两者不重叠、不冲突。

### 5.3 每日建议热量缺口

- 有生效计划：`avg_daily_deficit = (start_weight − target_weight) × 7700 / duration_days`。
- 无计划：−200 kcal/天。

### 5.4 营养素比例

柱状图与详情卡展示 `碳水:蛋白:脂肪`，按 3 项克数归一化（膳食纤维不参与）。

## 6. 核心业务流程

### 6.1 归属日与每日结转

- `业务今日 B = date(本地时间 − 2h)`。餐次、运动、聊天和看板中的“今日”均使用 B；身体测量日期仍使用用户选择的自然日期。
- 每日 02:00 后结转刚结束的归属日；当前归属日只从 `meal_entry` 实时聚合，绝不提前创建 `daily_summary`。
- `meal_entry` 只包含已经形成营养快照的正式明细；结转聚合该日全部正式明细。没有任何正式饮食记录的日期不创建汇总，看板显示为空缺而不是 0。
- 首次创建某日汇总时捕获 `bmr_snapshot`；资料不足时允许为空。若是延迟补跑，身体数据取日期不晚于目标日的最近测量。之后因补录而重算营养汇总时必须保留原快照，不用当前 BMR 覆盖历史。
- 启动补跑先扫描所有仍存在正式明细但缺少汇总的已结束日期并完成结转，再执行清理；不能只扫描最近 7 天，否则长时间关闭应用后可能丢失尚未结转的最后一天。
- 清理边界为当前归属日 B 之前的第 6 天：成功结转后删除 `date < B−6` 的餐次与聊天，从而保留 B 加前 6 个归属日，共 7 天。存在正式明细但尚未成功汇总的日期不得清理。
- 同一日期的明细增删改与已结束日汇总重算在同一数据库事务内完成。启动补跑不再依赖 `max(created_at)` 猜测是否有修改；正常写路径的事务一致性是唯一真源。

### 6.2 补录 / 修改

- 仅允许最近 7 个归属日；更早日期不允许创建或修改明细，也不允许直接编辑长期汇总。
- 对话产生的是“现有明细 + 待确认操作”的预览，不在 Confirm 前写入正式表。
- Confirm 后原子执行全部增删改。目标日等于 B 时只刷新实时聚合；目标日已结束时同步重算 `daily_summary`，并保留原 `bmr_snapshot`。
- 完成后退出补录模式并回到业务今日。

### 6.3 录入入口

文本、照片、手动录入和常吃库等所有食物业务路径以 §7 为唯一定义；本节不重复维护第二套流程。

### 6.4 对话历史

对话气泡与结构化业务数据完全解耦。显示历史按归属日保留 7 天并与餐次明细一并清理；删除聊天文本或图片不影响任何已落库业务数据。补录对话按发生时间进入当前聊天流，业务变更写入目标归属日。

显示历史不等于模型上下文：每次 LLM 调用只发送完成当前意图所需的消息、图片和结构化状态，不默认把 7 天完整历史全部发送给第三方。`chat_message` 至少记录 id、归属日、role、content、可空图片引用和 UTC created_at；图片的保存与备份口径见 §10。

## 7. 食物查询、录入与维护路径（唯一业务定义）

### 7.1 统一内部口径

所有入口在营养计算前归一为食物名、数量、单位、餐次和 `preparation_state`，其中单位只允许 `g` 或 `serving`。普通食物的“个、碗、盘、大份”等描述由 LLM 在本次解析中估算为可食部克重；`serving` 只表示已兼容命中的个人固定食谱。LLM 不生成营养值，清蒸、油炸、红烧等做法仍保留在食物名称中。

查询适配器从 §4.4 两个来源表生成临时统一候选，供本次匹配、确认和营养计算使用；临时候选不是第三张基础表，也不反写外部来源记录。外部候选只有 raw/cooked/unknown，不产生 recipe；不能可靠判断生熟状态时保持 unknown，等待用户确认。

### 7.2 四级查询链

按以下顺序逐级查询；每一级先完成本级候选召回与消歧，没有候选或用户确认“都不是”才进入下一级：

1. 个人常吃食物库；
2. 本地中国第六版 OCR 数据；
3. USDA FoodData Central；
4. 网络搜索证据 + LLM 结构化估算，标记 `web_estimate`。

每一级按同一规则处理：

1. 没有候选：进入下一级。
2. 只有一个兼容候选：直接采用并停止查询链。
3. 有多个兼容候选：把本级候选集合交给 LLM。LLM 只能从集合内选择；若其中存在语义上明确的日常常见项，则默认采用并停止查询链；若没有明确常见项，则向用户展示候选，由用户选择。
4. 用户选择“都不是”：进入下一级；第④级之后仍未选定则按 §7.6 继续追问。

“兼容”必须满足食物名称语义、`preparation_state` 和单位约束。`serving` 只能在第①级命中 recipe；未命中个人食谱时，必须先把自然语言份量估算为 g，才能继续查询第②–④级。候选数量本身不能成为跳过当前数据源的理由，LLM 也不得修改候选中的营养值或生成集合外选项。

### 7.3 单位与营养计算

内部营养统一锚定在每 100g 可食部，业务计算只接受两种单位：

- **g**：用于 raw/cooked 常吃食物及第②–④级候选。普通食物的自然语言份量由 LLM 做本次克重估算，不永久保存“碗/个/盘 → 克重”映射；营养按实际可食部克重与每 100g 标准值计算。
- **serving**：只用于 `preparation_state = recipe` 的个人常吃食谱。整份 `components` 定义一份，食谱按本次份数等比例计算，不再拆解查询组成项。

中国来源仅在用户明确给出带壳、带骨等总重时应用可食率；USDA 来源由适配器按其数据口径规范化为每 100g 候选。两个外部来源都不提供本系统的永久份量定义，详细接入限制只在 §4.4 维护。

### 7.4 确认与持久化矩阵

| 路径           | 条件                                                      | Confirm 前                                 | 正式写入                                                         |
| -------------- | --------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------------------- |
| 文本快速录入   | 字段完整，第①–③级得到单一兼容候选或 LLM 选出明确常见项 | 可直接展示计算结果                         | 立即写入正式明细，并提供撤销/编辑                                |
| 文本歧义       | 多候选且无明确常见项、生熟口径不明或克重估计可信度不足    | 追问/候选预览                              | 用户选择后写入                                                   |
| 照片估算       | 所有情况                                                  | 食物名称、生熟状态、克重、置信度和营养预览 | Confirm 后写入                                                   |
| 第④级网络估算 | 所有情况                                                  | 显示来源、置信度和“可能不准”             | Confirm 后写入                                                   |
| 手动录入       | 用户提交结构化表单                                        | 表单本身即确认界面                         | 查询得到可信营养结果才写入；未解析不写入，LLM 可用时转回聊天追问 |
| 历史补录/修改  | 最近 7 个归属日                                           | 展示整批 ops 对目标日的结果                | Confirm 后原子写入                                               |
| 常吃库增改删   | 见 §7.7                                                  | 展示目标记录及变化                         | 用户明确操作后写入                                               |

如果同一批里有的项满足直接写入、有的项需要用户确认，系统**单独弹出待确认的项。**

### 7.5 各录入路径

**A · 文本快速录入**：解析 → 归一为 g 或 serving → 逐级召回与候选消歧 → 营养计算。符合 §7.4 快速条件时直接写入；其余情况停在候选或确认态。

**B · 照片录入**：图片识别 → 生成每项食物名称、生熟状态和克重预览 → 用户调整/确认 → 四级查询与营养计算 → 写入。做法直接保留在食物名称中。多张图片只作为同一餐次的一组观察输入，由 LLM 合并同一食物，不能把不同视角重复记为两份。

**C · 手动录入**：普通食物填写克重和 raw/cooked，已存在的个人食谱填写份数；做法写入食物名，不提供独立制备方式控件。该入口绕过 LLM 解析，但仍执行同一四级查询；未得到可信营养结果时不写入 `meal_entry`，LLM 可用则转回聊天继续追问，不可用则明确提示未解析。

**D · 明细编辑/删除**：在单位不变时修改数量，按该明细保存的营养快照与新旧数量比例重算；在 g 与 serving 之间变化时，以食物名和新单位重新走解析、查询与必要确认路径。删除和重算遵循 §6 的事务规则，不回写常吃库。

**E · 历史补录**：LLM 或手动表单生成 add/update/delete 操作集 → 预览 → Confirm → 按 §6.2 原子执行。

### 7.6 无法解析与外部服务降级

- LLM 解析失败不影响手动录入入口；任一食物数据源失败时自动进入下一级。
- 第④级仍无法解析或用户不接受估算时，LLM 可用则在聊天中继续追问食物名称、克重或生熟状态等必要信息，补充后重新执行查询；LLM 不可用则明确提示未解析。
- 在得到可信营养结果前，不插入 `meal_entry`，不创建未提交草稿，也不提供独立的手填营养表单；当前交流只作为普通聊天历史保留。
- 系统不得用 0 或虚构值替代未知营养，避免把“缺失”误当成“确定为零”。

### 7.7 常吃食物库完整路径

常吃库逻辑只在本节维护：

1. **查询复用**：按食物名称语义、`preparation_state` 和 unit 召回候选，并统一按 §7.2 消歧；raw/cooked 按克重计算，recipe 按固定营养快照和本次份数计算。`meal_entry` 只写入归一后的数量、单位、营养快照和原 `source_tag`，不保存常吃库关联。
2. **从餐次保存**：普通 g 记录可利用仍在解析上下文中的标准营养、生熟状态和来源生成 raw/cooked 常吃候选；若从既有 `meal_entry` 发起，则重新查询并确认，不能假设短期行保存了这些食物库字段。
3. **主动创建食谱**：recipe 必须由用户明确创建并确认完整 `components`；每项只含食物名、克重和 raw/cooked，整份列表定义一份并生成固定营养快照。
4. **相似项检查**：写入前先按 category、生熟状态和名称/别名做后端粗筛；存在候选时再用 LLM 做语义辅助判断。LLM 只产生候选解释，不能自行覆盖。
5. **选择**：用户可新增为独立食物、选用已有项，或以新值更新已有项。所有对比同时显示五项营养、`preparation_state`、unit、食谱组成摘要和来源。
6. **更新**：按 `food_id` 定位，可修改名称、营养、`preparation_state`、unit 和食谱组成，但必须持续满足 §4.5 的约束；不回溯任何历史 `meal_entry`。
7. **删除**：按 `food_id` 删除，不影响历史餐次。

**待产品确认 OPEN-FOOD-01**：何时主动提示“保存到常吃库”仍未定，可选“每个新 resolved 食物都询问”“仅第④级/自制菜询问”或“完全由用户主动保存”。在该决策完成前，系统只提供显式“保存到常吃库”动作，不自动插入，也不由实现者自行选择提示策略。

### 7.8 来源与缺失值

每条营养数据只用一个 `source_tag` 表达来源，不再设置含义重叠的来源引用字段。常吃库复用不覆盖原来源；`web_estimate` 永久保留风险标记。第④级候选的置信度只用于确认界面，不另造来源字段。不同来源缺少某项营养素时使用 null 而不是 0；聚合和 UI 必须区分“未提供”和“确定为零”。

## 8. LLM 集成契约

所有 LLM 输出为严格 JSON（无 Markdown 围栏、无前后缀），解析失败时回退追问。

### 8.1 自然语言饮食解析

```json
{ "meal_slot": "lunch",
  "items": [
    { "food_name": "鸡胸肉", "quantity": 150, "unit": "g",
      "preparation_state": "raw" },
    { "food_name": "我的燕麦碗", "quantity": 1, "unit": "serving",
      "preparation_state": "recipe" }],
  "clarify": null }
```

仅产出食物名称、归一后的数量、g/serving、`preparation_state` 和餐次，不产出营养值。普通食物的自然语言份量在本次解析中估算为 g；已知个人食谱使用 serving。做法必须保留在 `food_name` 中，不另行结构化；无法可靠估算克重或信息不足时，`items` 为空并通过 `clarify` 追问。

候选消歧是独立于营养计算的 LLM 职责：系统把用户原始描述和当前查询级的候选集合一并提供给 LLM；LLM 只能返回“选择集合中的某一项”或“需要用户选择”。只有存在明确的日常常见项时才能自动选择，不能改写候选字段、组合多个候选或生成集合外食物。

### 8.2 照片估算

**输入**：食物照片（俯拍必需、侧拍可选）+ 握拳参照尺寸（length/width/height，cm，拳头入镜）。俯拍给面积，侧拍给高度，联合估体积/质量。提示 LLM 考虑透视与拍摄角度。侧拍可选：提供则体积/克重估计更准、置信度更高；缺侧拍不阻断，置信度相应下调并在 `confidence_reason` 注明。握拳参照物同理不阻断：用户尚未在「我的」录入握拳尺寸，或本次照片中未拍到拳头，均不阻断估算流程，但 LLM 需在 `confidence_reason` 中注明「缺少参照物，克重估计仅供参考」并相应下调 `confidence`（无参照物时不应给出 high）。

**输出**（必带生熟状态、置信度与可展示的判断依据）：

```json
{ "meal_slot": "lunch",
  "items": [
    { "food_name": "米饭", "preparation_state": "cooked",
      "grams_estimate": 200, "grams_low": 170, "grams_high": 240,
      "confidence": "medium", "confidence_reason": "俯拍清晰但缺侧拍，高度靠估" },
    { "food_name": "红烧肉", "preparation_state": "cooked",
      "grams_estimate": 150, "grams_low": 120, "grams_high": 190,
      "confidence": "medium", "confidence_reason": "部分被酱汁遮挡" }],
  "summary": "照片里是米饭和红烧肉，其中米饭大概熟重200g、红烧肉大概熟重150g",
  "clarify": null }
```

照片中的生熟状态由 LLM 根据画面估计，用户可在 Confirm 前修正；做法直接体现在食物名称中。生熟状态只用于 §7 的候选匹配，不替代数据库营养值。

**交互策略**：

- `summary`、`confidence` 和 `confidence_reason` 必须在确认界面可见；这里的 reason 是可展示证据，不要求输出模型内部推理链。
- 每项克重、生熟状态和食物名称必须可调整，具体控件和快捷步长由 UI 设计决定。
- 图片识别、克重估计和营养查库是三个独立阶段；所有照片路径均按 §7.4 Confirm 后写入。

### 8.3 补录对话契约

后端提供目标日现有明细作为上下文，LLM 输出增删改操作：

```json
{ "date": "2026-07-07",
  "ops": [
    { "action": "add", "item": { "food_name": "鸡蛋", "quantity": 50, "unit": "g",
      "preparation_state": "raw", "meal_slot": "lunch" } },
    { "action": "update", "target_id": 123, "quantity": 180 },
    { "action": "delete", "target_id": 130 }] }
```

LLM 只输出操作草稿；用户 Confirm 后按 §6.2/§7.5 执行。

### 8.4 常吃食物库操作契约

本节仅定义 LLM 可生成的结构化意图；查询、相似项检查、确认和写入语义只以 §7.7 为准。

```json
{ "action": "create_favorite_draft", "food_name": "我的燕麦碗", "category": "dish",
  "unit": "serving", "preparation_state": "recipe",
  "components": [
    { "food_name": "燕麦片", "grams": 40, "preparation_state": "raw" },
    { "food_name": "牛奶", "grams": 200, "preparation_state": "cooked" },
    { "food_name": "香蕉", "grams": 80, "preparation_state": "raw" }] }
```

```json
{ "action": "update_favorite_draft", "food_id": 42,
  "changes": { "components": [
    { "food_name": "燕麦片", "grams": 50, "preparation_state": "raw" },
    { "food_name": "牛奶", "grams": 200, "preparation_state": "cooked" },
    { "food_name": "香蕉", "grams": 80, "preparation_state": "raw" }] } }
```

```json
{"action":"delete_favorite_draft","food_id":42}
```

只有 recipe 允许生成 `components`，组成项只能是 raw/cooked；系统据此生成食谱营养候选，用户确认后固定为该食谱的营养快照。所有意图在用户确认前均可撤销。

### 8.5 第④级网络估算契约

前三级都没有兼容命中时，由 LLM 基于网络搜索证据结构化为内部每 100g 候选值：

```json
{ "food_name": "红烧肉", "preparation_state": "cooked",
  "kcal_100g": 250, "carb_100g": null, "protein_100g": 12, "fat_100g": 18, "fiber_100g": null,
  "confidence": "low" }
```

系统将该候选标注为 `source_tag = web_estimate`，不再另存来源引用字段。缺失营养素保持 null，不用 0 补齐；按 §7.4 必须确认后才能写入餐次。

### 8.6 运动对话解析契约（Closed Beta 起）

用户口述运动情况，LLM 只做「口语 → 结构化字段」的解析，不替用户估算强度或消耗（消耗 kcal 需由用户口述给出，缺失时追问，不由 LLM 编造）：

```json
{ "date": "2026-08-12",
  "items": [
    { "category": "cardio", "duration_min": 30, "kcal_burned": 250 }],
  "clarify": null }
```

字段与 `exercise_entry`/手动录入表单一一对应（§4.3、§2.2 E）。信息不足时追问；Confirm 后复用运动写入服务，`source_tag = dialogue`。

### 8.7 身体数据对话解析契约（Closed Beta 起）

用户口述身体数据，LLM 仅解析用户直接给出的数值，不做推断估算：

```json
{ "date": "2026-08-12",
  "fields": { "weight": 70.2, "body_fat_pct": null, "waist": null, "hip": null, "thigh": null, "calf": null },
  "clarify": null }
```

未提及的字段留空、不覆盖已有记录，与 §2.3 B 手动录入的 upsert 语义一致。Confirm 后复用身体数据写入服务，不保存录入来源字段。

### 8.8 多模态模型选型

模型必须支持中文、多图输入和可靠的结构化输出。Qwen3-VL 系列可作为首选候选，但核心 SPEC 不锁定具体版本或易过期的价格；后端通过供应商无关适配层接入，模型选择、成本比较与供应商保留政策记录在独立 ADR/配置中。

## 9. 后端接口边界

具体 REST 路径和 HTTP 动词属于实现设计，本 SPEC 只约束必须存在的能力：

- **饮食解析与写入**：解析预览、四级查询候选与 LLM 消歧、文本快速写入、照片/歧义确认、结构化手动录入、聊天追问及最近 7 日查询与增删改。
- **常吃库**：搜索/排序、按 `food_id` 增改删、单位与食谱组成维护、相似候选检查；行为以 §7.7 为准。
- **结转与看板**：内部结转/补跑、过去 7/14/30 日汇总、业务今日实时汇总。
- **运动**：按归属日查询、增加和删除；`source_tag` 记录 manual/dialogue。
- **身体数据**：按自然日期 upsert、窗口查询和最近非空值查询。手动与对话录入复用同一校验，不保存来源字段。
- **计划与个人信息**：计划设置/进度、基础信息与 BMR 查询。

跨入口复用相同业务服务和校验规则，不为对话、表单各维护一套写入逻辑。

## 10. 非功能性需求

- **私有持久化与外部处理**：业务数据库保存在单用户私有后端；LLM、USDA、网络搜索调用会把完成任务所需的文本、图片或查询词发送给第三方处理。产品必须在调用前披露出网类别，供应商应支持关闭训练或满足约定的数据保留政策，不能笼统承诺“第三方绝不留存”。
- **私有访问边界**：PWA 与 API 通过 HTTPS 安全上下文交付，后端只允许本人授权终端或受保护的私有入口访问，不提供公开注册或匿名业务接口。访问保护位于部署边界，不向业务表引入 `user_id`。API Key 只保存在私有后端配置/系统密钥存储中，不进入前端包、聊天记录、日志或导出文件。
- **PWA 边界**：系统必须具备可添加到手机主屏幕并独立启动所需的安装能力；具体缓存与更新实现可调整，但不能依赖宽屏布局或原生容器。电脑浏览器复用同一手机 UI。PWA 缓存只保证应用外壳和明确的离线提示，不提供离线业务写入或稍后同步。
- **可用性**：私有后端不可达时禁止提交业务写入并显示可恢复错误；LLM/USDA/网络任一失败时按 §7.6 逐级降级或回到聊天追问。手动录入入口始终可进入，但没有可信营养结果时不生成记录。
- **一致性**：明细写入和已结束日汇总重算遵循 §6 的事务边界；结转幂等且先补跑后清理。
- **备份与恢复**：支持导出和恢复。若聊天图片保存在 SQLite 外，备份产物必须是包含数据库与仍在保留期图片的归档包，不能再宣称“单个 SQLite 文件即完整备份”；也可选择把短期图片存为数据库 BLOB。
- **运行生命周期**：结转任务运行在私有后端，不依赖 PWA 在前台或手机允许浏览器后台运行；后端每次启动仍执行 §6.1 补跑。
- **性能**：趋势查询使用长期汇总；文本解析、照片解析和关键交互的具体 P95 指标在实现前的验收配置中确定，不在核心 SPEC 固定为“毫秒级”。

当前路线图不包含账号体系、多人数据隔离、本机数据库同步、公众开放、宽屏专属 UI 或原生 App。本人多台授权设备直接访问同一私有后端，不构成多副本同步。若未来改变任一边界，必须先修订 PRD，并通过专项设计重新评估身份、授权、数据迁移和冲突处理。出网披露、私有访问保护、密钥保护、供应商保留要求和备份恢复必须在 MVP 阶段落实。

## 11. 里程碑范围与验收标准（对照 PRD §9）

PRD §9 是产品范围基准；本节将其转换为系统启用边界和技术验收。两份文档发生冲突时必须显式同步修订，SPEC 不得自行覆盖 PRD 的产品范围。所有阶段都在同一套手机 UI PWA 和单用户私有后端上增量解锁，不存在后续宽屏版或原生 App 分支。

### 11.1 Demo — 饮食核心闭环

| 维度 | 系统范围 |
| ---- | -------- |
| 平台边界 | 建立可安装 PWA 与私有后端基础链路；手机竖屏为正式布局，电脑浏览器复用同一结构。 |
| 页面启用 | 「记录」启用文本对话、结构化手动录入和只读今日明细；「看板」只启用 A1 热量摄入趋势。「记录」照片入口、常吃库表格、看板其余组件及「我的」均不启用。 |
| 数据与系统逻辑 | 启用 `meal_entry`、`daily_summary`、`chat_message`、`food_base_cn` 和 `food_base_us`。餐次明细和对话按 §6 保留 7 个归属日，汇总永久保留；02:00 结转、启动补跑和幂等规则从 Demo 起生效。 |
| 饮食记录 | 文本与手动入口共用 §7 流程；四级链跳过第①级常吃库，从中国 OCR 数据开始。执行 g 归一、逐级候选消歧和确认矩阵，只允许当天新增与对话修正；今日表不开放直接编辑。 |
| 运动记录 | `exercise_entry` 及相关组件不启用。 |
| 身体数据 | `body_metric`、`user_profile`、`diet_plan` 及 BMR/计划组件不启用；`daily_summary.bmr_snapshot` 允许为空。 |
| LLM 范围 | 只启用 §8.1 饮食文本解析、§7.2 候选消歧和当天增删改草案；不启用照片、常吃库维护、运动和身体解析。 |

**技术验收（Demo → MVP）**：

- 文本解析合法结构率 ≥ 95%，候选选择不得超出当前候选集合。
- 文本/手动录入 → `meal_entry` → 今日明细 → 次日 `daily_summary` → A1 趋势链路无阻断性缺陷。
- 结转重复执行不重复累加；对话清理不影响已写入的业务记录。
- PWA 可在目标手机浏览器添加到主屏幕并独立启动；任何已启用功能均不依赖宽屏布局。

### 11.2 MVP — 三大模块完整闭环

| 维度 | 系统范围 |
| ---- | -------- |
| 平台边界 | 单用户私有后端成为唯一业务数据源；PWA 不维护可离线写入的第二份本机数据库。 |

## 12. 验证、边界场景与埋点范围

详细测试计划（测试层级、测试矩阵、CI 执行策略、Mock 数据、具体用例、优先级分级）不在本 SPEC 展开，维护为独立的 Test Plan 文档；各里程碑的验收标准见 §11。本章只说明系统设计层面必须覆盖的验证维度、关键边界场景，以及埋点需要覆盖的行为范围。

### 12.1 Validation Strategy（验证策略）

系统采用单元测试、集成测试、端到端验收测试与回归测试四层验证。单元测试覆盖核心计算与边界逻辑；集成测试覆盖数据库、外部数据源及 LLM 契约的模块协作；验收测试验证用户关键闭环；回归测试确保后续里程碑不破坏既有能力。

系统正确性主要从以下维度验证：

- **Functional Correctness（功能正确性）**：核心业务规则符合 §5–§8——BMR 双公式、每日总消耗与热量 Δ、减脂计划派生量、克数营养比例，以及 §7 的逐级候选消歧、g/serving、固定食谱与确认矩阵。
- **Data Consistency（数据一致性）**：短期库（`meal_entry`）与长期库（`daily_summary`）按 §6 的事务和结转规则保持一致；身体数据当前值按日期读取最近一次非空测量；补录/编辑后汇总与明细不出现对不上的情况。
- **LLM Contract Robustness（LLM 契约健壮性）**：§8 各契约的 JSON 输出合法率；候选消歧只能引用当前集合；信息不足时以 `clarify` 追问而非编造数值；照片估算的置信度/理由字段必填且可解释（§8.2）；解析失败时的回退行为。
- **External Dependency Degradation（外部依赖降级健壮性）**：LLM/USDA/网络搜索任一环节失败或限流时，正确进入下一查询级、结构化手动录入或聊天追问；未解析前不得生成业务记录（§7.6、§10）。
- **Performance（性能）**：趋势类查询基于已聚合的长期库数据，响应无感知延迟（§10）；对话解析、明细编辑保存等关键交互的响应时间可观测。

### 12.2 Critical Edge Cases（关键边界场景）

以下边界场景属于系统设计必须处理的正确性问题，而非可选的 QA 用例：

| 边界场景         | 位置              | 系统设计要求                                                                                                                   |
| ---------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 结转幂等与补跑   | §6.1             | 重复触发同一归属日结转不得重复累加；启动时先处理所有仍有明细但缺汇总的已结束日期，再清理；补录重算保留原 BMR 快照。            |
| USDA 429 限流    | §7.6             | 查询失败/限流时进入第④级；仍未解析则回到聊天追问，获得可信营养结果前不生成业务记录。                                          |
| LLM JSON Invalid | §8               | 解析结果非合法 JSON 或结构不符契约时回退追问，不静默失败、不猜测填充。                                                         |
| Clarify 触发     | §8.1/§8.6/§8.7 | 信息不足（如未说明数量、普通食物无法可靠估算克重、缺消耗 kcal）时返回追问而非编造数值，`items`/`fields` 相应留空。         |
| 查询多候选       | §7.2/§8.1       | 当前级候选全部交给 LLM；有明确日常常见项才自动选择，否则展示给用户。LLM 不得选择集合外食物，用户选择“都不是”后才进入下一级。 |
| 相似食物名误判   | §7.7             | LLM 判定为同一食物但用户在选择交互中确认不是时，不得已经写入/覆盖`food_favorite`；判定结果在用户确认前必须可撤销。           |

### 12.3 Analytics Scope（埋点范围）

以下行为类别需要被追踪：对话解析成功率与延迟、食物查询来源分布、结转状态、常吃库候选确认结果和关键页面耗时。当前路线图只在私有后端聚合，不发送到第三方分析服务；具体事件名和属性由独立 Analytics Tracking Spec 定义。

```
归属日     = date(本地时间 − 2h)     // 业务归属
created_at = UTC-0 时间戳            // 绝对真时间 / 审计

   本地 2026-07-08 02:30 → 归属 2026-07-08
```
