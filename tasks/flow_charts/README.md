# tasks/flow_charts/ — 业务流程 ↔ 代码映射

## 这套文档解决什么问题

PRD/SPEC 定义业务规则,STATUS.md/current.md 追踪"现在要做什么",但两者都不回答
"这个业务环节现在由哪些函数/组件负责"。跟 Claude Code/Codex 讨论代码时,双方经常
在说函数名,而人脑子里想的是业务环节——这套文档补上这道"业务环节 ⇄ 代码"的翻译层。

**它不是**:

- 完整测试计划(测试细节仍以 `tests/backend/`/`frontend/src/tests/` 本身为准);
- 穷举所有异常分支的状态机(current.md 已有的完整状态机不重复搬过来);
- 业务规则的定义来源(规则以 PRD/SPEC 为准,这里只画"规则由谁实现")。

它维护的核心是一件事:**业务环节 → 组件/API/函数/class → 输入输出** 的对应关系。

## 文件

- `00_demo_overview.md` — Demo 1.1~1.13 业务流程总览,一页看清楚整条用户旅程
  经过哪些环节、每个环节对应哪个里程碑、去哪个文件看细节。
- `01_0608_food_query.md` — 1.6~1.8:食物营养查询引擎(文本解析 + 营养估算)。
- `01_09_write_path.md` — 1.9:写入 + 今日明细 UI(计划中)。
- 以后每个 STATUS 小步一个文件,命名 `01_<步骤号去掉小数点>_<关键词>.md`
  (如 `01_10_carryover_trend.md`、`01_11_body_metrics_bmr.md`、
  `01_12_exercise_overlay.md`);前缀 `01` 对应 PRD/SPEC 的 Demo 里程碑,以后若
  开 MVP/Closed Beta 阶段再启用 `02_`/`03_` 前缀。

## 标注图例

- `[现有]` — 代码已经存在,写文档前已用 Read/Grep 核实过。
- `[NN计划]`(如 `[1.9计划]`)— current.md 中已写好设计但尚未实现;NN 对应STATUS.md 的步骤号。
- `[后续]` — 属于更后面的步骤,尚无 current.md 级别的详细设计,只有 STATUS.md表格里一行描述。
- `[名称未定]`(用在函数级图里)/`[文件未定]`(用在 `00_demo_overview.md` 这种文件级图里)— 业务职责已经明确,但具体代码位置(文件/函数/组件)还没定下来(还没写 current.md 或还在设计阶段)。

## 流程图排版约定

流程图统一用 Mermaid(` ```mermaid ` 代码块,`flowchart TD`/`flowchart LR`),不用纯文本箭头或 `┌│└┼` 这类 box-drawing 字符手工画——手工对齐在中英文混排、不同渲染环境(终端/编辑器/网页)下容易错位,Mermaid 由渲染器负责布局,不依赖字符宽度对齐,GitHub/VS Code 都能原生渲染。

- 每个 mermaid 代码块第一行统一加:`%%{init: {'themeVariables': {'fontSize': '11px'}, 'flowchart': {'nodeSpacing': 15, 'rankSpacing': 18, 'padding': 4}}}%%`——调小字号、缩小节点间距/层级间距,信息密度优先,尽量让一张图不用滚动就能看完。
  Mermaid 经典渲染器不提供"文字贴边框"这种节点内边距的直接开关,真正影响框大小的是文字长短,所以节点文字要精简(见下一条),不要用长句。
- 节点文字用双引号包裹(`["文字"]`),避免中文/符号被 Mermaid 语法误解析;换行用`<br/>`;能不换行就不换行,文字尽量短——图是给人一眼扫过去定位环节用的,不是给人在图里读完整业务描述,完整措辞看表格或正文。
- **图里不要放"详见 xxx.md"这类跳转节点**(不要为了指向另一个文件专门画一个框和一条虚线)。文件之间的引用关系放在图外的正文文字里(一句话提一下),不占流程图的空间和阅读路径。
- **节点顺序按实际业务执行顺序排列,不按里程碑号、不按 Feature Branch 分组**。同一次用户操作里,不同里程碑的代码经常互相包裹调用——比如 1.9 的消息发送入口在时间线上位于 1.6~1.8 的解析/估算**之前**触发,1.9 的确认卡片/写入又在其**之后**——按里程碑分组(不管是排版顺序还是用 `subgraph` 画区块)会让读者误以为"先做完一个里程碑的所有代码,再进入下一个",掩盖真实调用顺序。**不要用`subgraph` 给流程按里程碑/分支分区**;里程碑号写进节点文字第一行的括号里(如"用户发消息(1.9)"),按代码真实被调用的先后顺序摆放节点。
- **节点内容**:第一行写"业务环节(里程碑号)"(业务环节措辞和"业务环节 → 代码"表格里一致)。第二行的粒度按文件层级区分:

  - `00_demo_overview.md`(总览级)写**文件名**,不写函数名——总览只回答"归哪个文件管",函数级细节交给对应的详细文件,避免总览图信息过密。
  - `01_xx_xxx.md`(单个里程碑的详细文件)写**函数/组件名**,和文件自己的"业务环节 → 代码"表格一一对应,不要图里有表格里没有、或表格里有图里没有。
  - 颜色(见下面 `classDef`)不能替代文字标注状态——**加第三行写状态标签**:已有文件/函数写 `[现有]`,已规划未实现写 `[计划]`,未设计写
  - `[后续,文件未定]`(或函数级图里的 `[后续,名称未定]`)。这里统一用不带里程碑号的短标签(`[计划]` 不是 `[NN计划]`)——里程碑号已经在第一行括号里出现过,标签里再重复一遍是冗余;表格里因为那一行本身不重复出现里程碑号,所以仍然用完整的 `[NN计划]`(见上面"标注图例")。
- **条件分支必须有菱形判断节点**,菱形里写清楚"是哪个函数返回值的哪个字段"
  (例如 `parse_diet_text 返回的 DietParseResult.outcome`),不能只在边上标
  `resolved` 却不说明这个值从哪来。
- 用 `classDef`/`class` 按**泳道**(这一步实际由谁执行/落在哪一层)上色,**不按
  完成状态上色**——完成状态已经是第三行的文字标签(见上一条),颜色腾出来表达
  "这一步是谁在做",两个维度不用同一个视觉通道表示,同时看得更清楚:

  - `user`(用户操作 / 用户看到的结果,没有对应代码文件)→ 灰色系
    `#F4F5F3`/`#8A9088`。
  - `frontend`(Front end,React 组件/页面)→ 蓝色系 `#DCEAF7`/`#3B7BB8`。
  - `router`(后端 HTTP 入口,FastAPI Router)→ 紫色系 `#EAE3F5`/`#7B5EA8`。
  - `service`(Backend Service,纯业务逻辑/编排/计算,不直接对外发请求、不直接
    读写数据库)→ 绿色系 `#D4EADC`/`#2E8B62`(design.md 主色)。
  - `llm`(这一步的核心动作是调用 LLM)→ 琥珀色系 `#FDEBD3`/`#C97A2B`。
  - `db`(这一步的核心动作是读写 SQLite)→ 青色系 `#D6EFEC`/`#1F8A82`。

  判断归哪条泳道看"这一步实际在做什么",不是看文件放在哪个目录——比如
  `parse_diet_text` 物理上是 `services/` 目录下的一个函数,但它这一步的本质是
  "调用 LLM 拿解析结果",算 `llm` 泳道,不是 `service`;`confirm_meal_entry`
  同理算 `db` 泳道(核心动作是写 `meal_entry`),不是 `service`。判断分支的
  菱形节点归它所在的编排逻辑那条泳道(通常是 `service`)。
- 只画主路径和分支去向,不把错误细节画进图里——错误细节留给"需要考虑的错误情况"
  一节的 bullet list(呼应维护规则第 6 条)。

## 维护规则

1. 每个 STATUS 小步对应一个流程文件。
2. 业务流程编号保持稳定,不随函数改名重新编号。
3. 函数改名时只更新代码映射,不改业务编号或流程结构。
4. 新增、修改或删除业务环节时,同步更新对应流程图和 `CHANGELOG.md`。
5. 实现前标 `[NN计划]`;真实代码写完并核对过(不是"看起来该有了")才能改成
   `[现有]`。
6. 只展示主要业务路径;错误处理统一收进一节"需要考虑的错误情况",按 MECE 原则列 bullet points,不展开成决策树分支。
7. 测试文件映射单独成一张表,不混进主业务流程图里。
8. 业务环节映射表格式固定为:`业务环节 | 函数/组件 | 输入 | 输出 | 泳道 | 文件位置`——"泳道"取值就是上面 `classDef` 定义的六个泳道中文名(用户操作/Frontend/后端HTTP入口/Backend Service/LLM/SQLite),和流程图节点的颜色分类对应;文件路径始终放最后一列,不和函数名拼在同一格里。
9. **一个里程碑的文件不能只画"这个里程碑自己新增的代码"**,要把实际会调用到的、属于其它里程碑的函数也画进流程图、写进表格,并如实标注它真实所属的里程碑号和 `[现有]`/`[NN计划]` 状态——比如 1.9 的 `handle_new_message` 内部真实调用了1.8 的 `parse_diet_text`、1.7 的 `estimate_items`,这两步必须在 1.9 的文件里出现(标 `(1.8)`/`(1.7)` + `[现有]`),不能因为"不是 1.9 新写的"就省略,否则读者看不出这些已有函数在这个业务环节里具体处在什么位置。
